डिफ़ॉल्ट रूप से Blume `.md`/`.mdx` फ़ाइलों का एक फ़ोल्डर पढ़ता है। **कंटेंट स्रोत** आपको कहीं और से पेज लाने देते हैं — किसी रिमोट रिपॉज़िटरी, किसी CMS, या किसी भी कस्टम बैकएंड से — और कई स्रोतों को एक ही साइट में मिलाने देते हैं। स्रोत बिल्ड टाइम पर पढ़े जाते हैं; Blume स्टैटिक-फ़र्स्ट ही रहता है।

## डिफ़ॉल्ट [#the-default]

बिना किसी कॉन्फ़िगरेशन के, Blume आपके कंटेंट रूट (डिफ़ॉल्ट रूप से `docs`) को एक फ़ाइलसिस्टम स्रोत के रूप में स्कैन करता है। टॉप-लेवल `content.root`, `content.include` और `content.exclude` विकल्प उसी एकल स्रोत के लिए शॉर्टहैंड हैं — न कुछ इंपोर्ट करना है, न कुछ बदलना है।

```ts blume.config.ts
import { defineConfig } from "blume";

export default defineConfig({
  content: { root: "docs" },
});
```

## एडैप्टर [#adapters]

`content.sources` की हर एंट्री एक **एडैप्टर** है: `blume/sources` से इंपोर्ट की गई एक फ़ैक्टरी, जो एक सादा डिस्क्रिप्टर लौटाती है जिसे Blume बिल्ड टाइम पर पढ़ता है। स्रोतों को जोड़ने के लिए एक `sources` ऐरे जोड़ें। जब `sources` मौजूद होता है, तो यह निहित डिफ़ॉल्ट की जगह ले लेता है, इसलिए अपने लोकल डॉक्स के लिए एक `filesystem()` एंट्री शामिल करें — और `root`, `include` या `exclude` को उसके अंदर ले जाएँ। शॉर्टहैंड और `sources` को एक साथ इस्तेमाल नहीं किया जा सकता; Blume बताता है कि किस फ़ील्ड को ले जाना है।

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, mdxRemote } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      // Local docs at the site root
      filesystem({ root: "docs" }),

      // Remote MDX from a GitHub repo, mounted under /sdk
      mdxRemote({
        prefix: "sdk",
        github: { owner: "acme", repo: "sdk", ref: "main", path: "docs" },
      }),
    ],
  },
});
```

हर बिल्ट-इन एडैप्टर `blume/sources` से एक्सपोर्ट की गई एक फ़ैक्टरी है, जिसका वर्णन नीचे उसके अपने सेक्शन में किया गया है, और [`custom()`](#custom-sources) किसी भी अन्य बैकएंड को जोड़ता है। विकल्प ऑब्जेक्ट लेने वाला हर एडैप्टर दो साझा विकल्प स्वीकार करता है:

- **`prefix`** स्रोत के रूट को `/<prefix>/…` के अंतर्गत नेमस्पेस करता है, और यही डायग्नोस्टिक्स में स्रोत का नाम तथा उसकी कैश डायरेक्टरी भी बन जाता है। अगर दो स्रोत एक ही रूट पर पहुँचते हैं, तो Blume एक `BLUME_DUPLICATE_ROUTE` बिल्ड एरर रिपोर्ट करता है — हर स्रोत को एक अलग `prefix` दें।
- **`pollInterval`** (सेकंड में) डेव में किसी रिमोट स्रोत को उस अंतराल पर फिर से फ़ेच करवाता है, और तभी रीलोड करता है जब कंटेंट वास्तव में बदलता है। एक बार फ़ेच करके सेशन के लिए फ़्रीज़ करने के लिए इसे अनसेट छोड़ दें। लोकल स्रोत (`filesystem()`, `obsidian()`) इसके बजाय फ़ाइलसिस्टम पर नज़र रखते हैं और इसे अनदेखा करते हैं।

`custom(source)` इसका अपवाद है: यह किसी विकल्प ऑब्जेक्ट के बजाय एक `ContentSource` इंस्टेंस लेता है, इसलिए `prefix` या `pollInterval` पास करने की कोई जगह नहीं है। स्रोत अपनी `prefix` प्रॉपर्टी स्वयं सेट करता है, और फिर से फ़ेच करना वही होता है जो उसकी `watch` मेथड लागू करती है।

किसी एडैप्टर का डिस्क्रिप्टर यह भी घोषित करता है कि उसे किस SDK की ज़रूरत है और वह कौन-से एनवायरनमेंट वेरिएबल पढ़ता है, इसलिए जेनरेट किया गया प्रोजेक्ट उस पैकेज को घोषित करता है, कोई वेरिएबल अनसेट होने पर `blume dev` और `blume build` चेतावनी देते हैं, और `blume doctor` कॉन्फ़िगर किए गए स्रोतों की सूची दिखाता है। कॉन्फ़िग लोड होते समय विकल्पों की पुष्टि की जाती है: कोई छूटा हुआ आवश्यक विकल्प, कोई अज्ञात कुंजी, या 1.x का बचा हुआ कोई `{ type: "…" }` ऑब्जेक्ट एक ऐसे संदेश के साथ विफल होता है जो सुधार बताता है।

एकल `filesystem()` स्रोत जेनरेट किए गए डॉक्स कलेक्शन को अपनी ही डायरेक्टरी पर रूट करता है। कई फ़ाइलसिस्टम स्रोतों को एक ही रूट डायरेक्टरी साझा करनी चाहिए और उसे `include` ग्लॉब से विभाजित करना चाहिए — कहीं और रूट किया गया दूसरा स्रोत `BLUME_ENTRY_ID_MISMATCH` के रूप में रिपोर्ट किया जाता है, ताकि उसके पेज चुपचाप 404 न हों।

## Obsidian

बिल्ट-इन `obsidian()` एडैप्टर किसी [Obsidian](https://obsidian.md) वॉल्ट को उसी जगह पढ़ता है। कोई एक्सपोर्ट चरण नहीं है और आपके रिपॉज़िटरी में कुछ भी जेनरेट नहीं होता: वॉल्ट ही सत्य का स्रोत बना रहता है, और Blume लोड करते समय Obsidian की बोली को Markdown में उतार देता है।

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, obsidian } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      obsidian({
        prefix: "notes",
        vault: "vault",
        // Vault folder names to skip at any depth, on top of dot-folders
        exclude: ["Templates", "Daily"],
      }),
    ],
  },
});
```

`[[Wikilinks]]` रूट लिंक बन जाते हैं, जिन्हें पथ के बजाय पूरे वॉल्ट में नोट के नाम से संबोधित किया जाता है — ठीक उसी तरह जैसे Obsidian नोट्स को संबोधित करता है। कस्टम लिंक टेक्स्ट (`[[Note|label]]`), शीर्षक ऐंकर (`[[Note#Install]]`), पूरे पथ (`[[folder/Note]]` और `[[folder/Note.md]]`), वे आंशिक पथ जो Obsidian की डिफ़ॉल्ट "shortest path when possible" सेटिंग लिखती है (`[[guides/Note]]`), और `[[Note\|label]]` रूप जो Obsidian किसी टेबल सेल के अंदर लिखता है — ये सभी काम करते हैं, और जो नोट अपने फ़्रंटमैटर में `slug` सेट करता है, उसे उस रूट पर लिंक किया जाता है जिस पर वह slug प्रकाशित होता है। जब दो नोट्स का नाम एक ही होता है, तो वह नोट जीतता है जिसका पूरा वॉल्ट पथ ठीक वही नाम है — Obsidian किसी लिंक को नाम से पहले पथ के रूप में हल करता है — उसके बाद वॉल्ट क्रम में पहला (नोट्स से पहले फ़ोल्डर, केस-असंवेदनशील रूप से, Obsidian के फ़ाइल एक्सप्लोरर की तरह)। Blume केवल तभी चेतावनी देता है जब कोई विकिलिंक वास्तव में ऐसी टकराहट से होकर हल होता है; अस्पष्टता दूर करने के लिए एक लंबा पथ लिखें। कोई ब्लॉक रेफ़रेंस (`[[Note#^id]]`) अपने नोट से बिना ऐंकर के लिंक होता है: ब्लॉक बिना किसी ऐसी id के रेंडर होते हैं जिस पर पहुँचा जा सके। कोई शीर्षक ऐंकर लक्ष्य नोट के वास्तविक शीर्षकों के सापेक्ष हल होता है, जिनका मिलान उसी तरह किया जाता है जैसे Obsidian का ऑटोकम्प्लीट उन्हें लिखता है (`**bold**`, `` `code` `` और लिंक सिंटैक्स हटाकर) और जिन्हें उसी `extractHeadings` पास द्वारा slug किया जाता है जो पेज मैनिफ़ेस्ट भरता है — इसलिए `#Install` का लिंक शीर्षक पर पहुँचता है, न कि किसी ऐसी id पर जो कोई पेज उत्सर्जित ही नहीं करता। `[[#Install]]` उस नोट के किसी शीर्षक को संबोधित करता है जिसे आप लिख रहे हैं। किसी ऐसे शीर्षक का लिंक जो मौजूद नहीं है, पेज लिंक बनाए रखता है, ऐंकर हटा देता है, और चेतावनी देता है।

फ़्रंटमैटर वही रखता है जो Blume का [पेज स्कीमा](/docs/content/frontmatter) स्वीकार करता है, साथ ही वह हर कुंजी जिसे आप [`frontmatter.extend`](/docs/content/frontmatter#custom-keys) में घोषित करते हैं (या, उस `type` के नोट्स के लिए, किसी कंटेंट टाइप का `frontmatter`); हर दूसरी Obsidian प्रॉपर्टी — Dataview फ़ील्ड्स, Templater तिथियाँ, `publish`, और Obsidian की अपनी `tags`, `aliases` और `cssclasses` — नोट के उतारे जाने पर हटा दी जाती है, इसलिए Properties UI से लिखा गया वॉल्ट बिना फ़्रंटमैटर एरर के बिल्ड होता है। `aliases` को हल करने के बजाय हटा दिया जाता है — उपनाम लिंक लक्ष्य अभी समर्थित नहीं हैं। किसी नोट के बगल में मौजूद कोई सापेक्ष Markdown इमेज (`![chart](./chart.png)`) वॉल्ट से परोसी जाती है, और जब वॉल्ट आपकी git रिपॉज़िटरी के अंदर रहता है, तो वॉल्ट पेजों को किसी भी अन्य पेज की तरह git से प्राप्त ["Last updated" तिथियाँ](/docs/configuration#last-modified) मिलती हैं। "Edit this page" लिंक `github.dir` के ज़रिए हल होते हैं, इसलिए किसी मोनोरेपो में डॉक्स ऐप के बगल में बैठा वॉल्ट भी अपनी फ़ाइल से लिंक होता है; रिपॉज़िटरी के बाहर मौजूद वॉल्ट को कोई लिंक नहीं मिलता।

वॉल्ट के अंदर लोकेल डायरेक्टरियाँ और वर्ज़न स्नैपशॉट उसी तरह पढ़े जाते हैं जैसे फ़ाइलसिस्टम स्रोत उन्हें पढ़ता है: [i18n](/docs/content/i18n) कॉन्फ़िगर होने पर `fr/Note.md` `/fr/` के अंतर्गत प्रकाशित होता है, [वर्ज़न](/docs/content/versioning) के साथ `v1.0/Note.md` `/v1.0/` के अंतर्गत, और उन नोट्स के विकिलिंक उस रूट की ओर इशारा करते हैं जिस पर हर एक प्रकाशित होता है।

:::note
जिस शीर्षक में स्वयं कोई लिंक होता है, उसका मैनिफ़ेस्ट ऐंकर शीर्षक के Markdown से आता है और उसका रेंडर किया गया `id` उसके टेक्स्ट कंटेंट से। उस शीर्षक के लिए ये दोनों भिन्न होते हैं, इसलिए उसका कोई विकिलिंक सेक्शन के बजाय पेज पर पहुँच सकता है।
:::

किसी `index` नोट का लिंक किसी काल्पनिक `/index` के बजाय उसके फ़ोल्डर के रूट पर पहुँचता है। **कोई अनसुलझा विकिलिंक बिल्ड को विफल करने के बजाय एक बिल्ड चेतावनी के साथ सादे टेक्स्ट तक सीमित हो जाता है**, इसलिए रीफ़ैक्टर के बीच का वॉल्ट भी प्रकाशित होता रहता है। एकल-पंक्ति `%%comments%%` हटा दिए जाते हैं, किसी HTML कमेंट के अंदर का विकिलिंक (`<!-- [[Draft]] -->`) वैसा ही छोड़ दिया जाता है क्योंकि Obsidian भी उसे छिपाता है, और जिस नोट के फ़्रंटमैटर में `title` नहीं होता उसका शीर्षक उसकी फ़ाइल के नाम से बनता है — वही नियम जो Obsidian स्वयं लागू करता है। `index` नोट एकमात्र अपवाद है: यह किसी नोट के बजाय किसी रूट का नाम बताता है, इसलिए उसका शीर्षक Blume की सामान्य व्युत्पत्ति पर चला जाता है (पहला शीर्षक, फिर मानवीकृत सेगमेंट)। फ़ेंस्ड, इंडेंटेड और इनलाइन कोड हूबहू पास हो जाता है, इसलिए इस सिंटैक्स का दस्तावेज़ीकरण करने वाला नोट बच जाता है।

डॉट-फ़ोल्डर छोड़ दिए जाते हैं, जिनमें Obsidian की अपनी `.obsidian` कॉन्फ़िग डायरेक्टरी और `.trash` शामिल हैं — जिन्हें डेव वॉचर भी अनदेखा करता है, इसलिए ऐप में कोई पैन हिलाने या किसी नोट को ट्रैश में डालने से आपकी साइट दोबारा बिल्ड नहीं होती। किसी नोट को संपादित करने से होती है। वे डायरेक्टरियाँ जिन्हें कोई भी कंटेंट स्कैन नहीं पढ़ता (`node_modules`, `dist`, `.git`, …) भी छोड़ दी जाती हैं, इसलिए प्रोजेक्ट में ही रूट किया गया वॉल्ट डिपेंडेंसी README प्रकाशित नहीं करता। वॉल्ट के अंदर के सिमलिंक का अनुसरण किया जाता है, उसी तरह जैसे फ़ाइलसिस्टम स्रोत उनका अनुसरण करता है, इसलिए वॉल्ट में लिंक किया गया कोई शेयर्ड फ़ोल्डर उसके साथ प्रकाशित होता है। फ़ाइलसिस्टम स्रोत के रूट के अंदर बैठे वॉल्ट को उससे बाहर रखा जाना चाहिए (`filesystem({ root: "docs", exclude: ["vault/**"] })`); तब [`blume version <id>`](/docs/cli/version) उसे स्नैपशॉट से बाहर छोड़ देता है, क्योंकि वॉल्ट अपने नोट्स को वर्तमान के रूप में प्रकाशित करता रहता है।

अभी तक नहीं उतारा गया: कॉलआउट (`> [!note]`) सादे ब्लॉककोट के रूप में रेंडर होते हैं, एम्बेड (`![[image.png]]`) अछूते पास हो जाते हैं, बहु-पंक्ति `%%comments%%` जहाँ के तहाँ छोड़ दिए जाते हैं, और कोई बैकलिंक ग्राफ़ नहीं है।

## रिमोट MDX [#remote-mdx]

बिल्ट-इन `mdxRemote()` एडैप्टर HTTP पर रॉ `.md`/`.mdx` फ़ेच करता है। फ़ाइलों की सूची या तो किसी GitHub रिपॉज़िटरी सबट्री (`github`) से बनाएँ या किसी रॉ बेस URL के सापेक्ष स्पष्ट रूप से (`url` + `files`):

```ts blume.config.ts
mdxRemote({
  prefix: "sdk",
  url: "https://raw.githubusercontent.com/acme/sdk/main/docs",
  files: ["intro.mdx", "guide.mdx"],
});
```

किसी प्राइवेट रिपॉज़िटरी का टोकन `GITHUB_TOKEN` एनवायरनमेंट वेरिएबल से पढ़ा जाता है — एडैप्टर इसे घोषित करता है, इसलिए इसके अनसेट होने पर `blume dev` और `blume build` चेतावनी देते हैं। यह कभी भी आपके कॉन्फ़िग या जेनरेट किए गए आउटपुट में इनलाइन नहीं किया जाता, और यह केवल GitHub के अपने होस्ट (`api.github.com`, `raw.githubusercontent.com`) पर ही भेजा जाता है, किसी कस्टम `url` बेस पर कभी नहीं। कोई पब्लिक रिपॉज़िटरी इसके बिना भी काम करती है।

रिमोट पेज पूरी MDX-प्लस-कंपोनेंट सटीकता के साथ रेंडर होते हैं: उनकी बॉडी एक छिपी हुई स्टेजिंग डायरेक्टरी में मटीरियलाइज़ की जाती है और आपके लोकल डॉक्स के साथ Astro के ज़रिए रेंडर की जाती है, इसलिए कॉलआउट, टैब और हर दूसरा Blume कंपोनेंट काम करता रहता है।

### कैशिंग और ऑफ़लाइन बिल्ड [#caching-and-offline-builds]

हर रिमोट स्रोत `.blume/cache/<source>/` के अंतर्गत एक स्नैपशॉट रखता है। अगर कोई फ़ेच विफल हो जाता है — कोई नेटवर्क गड़बड़ी या CMS आउटेज — तो Blume बिल्ड को विफल करने के बजाय चेतावनी के साथ आखिरी ज्ञात-अच्छा स्नैपशॉट परोसता है। प्रीव्यू और प्रकाशित कंटेंट को अलग-अलग स्नैपशॉट मिलते हैं, और स्रोत विकल्पों के हर सेट को भी, इसलिए कोई बिल्ड कभी भी `--preview` के तहत फ़ेच किए गए ड्राफ़्ट पर वापस नहीं जाता, और किसी स्रोत की `query` या `fields` संपादित करने पर वह नए सिरे से फ़ेच होता है। कैश `.blume/` के अंदर रहता है और फिर से जेनरेट होता है, कभी कमिट नहीं किया जाता।

डेव में, किसी रिमोट स्रोत का स्नैपशॉट मौजूद होने पर उसे उसी स्नैपशॉट से परोसा जाता है, इसलिए डेव सर्वर को पुनः आरंभ करने से वह फिर से फ़ेच नहीं होता। नवीनतम कंटेंट खींचने के लिए `blume sync` चलाएँ (चल रहा डेव सर्वर हॉट-रीलोड करता है), या पहले स्नैपशॉट हटाने के लिए `blume sync --force` चलाएँ। लोकल फ़ाइलसिस्टम स्रोत हमेशा की तरह हॉट-रीलोड होते हैं। इसके बजाय किसी रिमोट स्रोत में बदलावों के लिए पोल करने के लिए, उस पर साझा `pollInterval` विकल्प (सेकंड में) सेट करें — डेव सर्वर उस अंतराल पर फिर से फ़ेच करता है और तभी रीलोड करता है जब कंटेंट वास्तव में बदलता है। काम करते समय API पर बार-बार अनुरोध भेजने से बचने के लिए इसे अनसेट छोड़ दें।

## GitHub रिलीज़ [#github-releases]

बिल्ट-इन `githubReleases()` एडैप्टर किसी रिपॉज़िटरी की रिलीज़ को एक चेंजलॉग में बदल देता है: हर रिलीज़ एक `type: changelog` एंट्री बन जाती है, इसलिए आपके रिलीज़ नोट्स _ही_ आपका चेंजलॉग हैं — दो बार लिखने की ज़रूरत नहीं। जेनरेट की गई [चेंजलॉग टाइमलाइन](/docs/advanced/changelog) के साथ मिलकर, एक GitHub रिलीज़ प्रकाशित करना एक चेंजलॉग एंट्री भेज देता है।

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, githubReleases } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "content" }),
      githubReleases({
        prefix: "changelog",
        owner: "acme",
        repo: "sdk",
        // prereleases: false,  // include prereleases (default off)
        // drafts: false,       // include drafts (needs a write token)
        // limit: 100,          // cap releases, newest-first
      }),
    ],
  },
});
```

हर रिलीज़ अपने आप चेंजलॉग फ़ील्ड्स से मैप हो जाती है: उसका नाम (या टैग) शीर्षक बन जाता है, उसकी प्रकाशन तिथि टाइमलाइन क्रम तय करती है, टैग `changelog.version` बन जाता है, और प्रीरिलीज़ को `Prerelease` टैग किया जाता है (बाकी को `Release`)। नोट्स एंट्री की बॉडी के रूप में रेंडर होते हैं, और उनके लिंक में दो बदलाव किए जाते हैं: जो लिंक वेब, मेल, फ़ोन या सापेक्ष पता नहीं है (मान लीजिए कोई `javascript:` URL), वह केवल अपना लेबल बनाए रखता है, और आपकी अपनी [`deployment.site`](/docs/deployment) की ओर वापस जाने वाला लिंक उसके रूट-सापेक्ष पथ में दोबारा लिखा जाता है, ताकि वह प्रीव्यू डिप्लॉय और आपके डिप्लॉयमेंट बेस का अनुसरण करे। स्रोत को एक `prefix` दें ताकि उसके रिलीज़ पेज `/changelog/v1-2-0` जैसे रूट के अंदर नेस्ट हों।

एक प्राइवेट रिपॉज़िटरी `GITHUB_TOKEN` एनवायरनमेंट वेरिएबल से प्रमाणित होती है — वही टोकन जो अन्य GitHub फ़ीचर इस्तेमाल करते हैं, कभी भी आपके कॉन्फ़िग में इनलाइन नहीं किया जाता; एडैप्टर इसे घोषित करता है, इसलिए इसके बिना बिल्ड चेतावनी देता है। हर रिमोट स्रोत की तरह यह भी `.blume/cache/<source>/` के अंतर्गत कैश होता है और API अनुपलब्ध होने पर ऑफ़लाइन परोसा जाता है। चूँकि चेंजलॉग पूरक होता है, इसलिए बिना कैश के फ़ेच विफलता (मान लीजिए बिना टोकन वाला कोई CI बिल्ड) बिल्ड को विफल करने के बजाय चेतावनी के साथ एक खाली चेंजलॉग तक सीमित हो जाती है — इसे भरने के लिए अपने CI और डिप्लॉय एनवायरनमेंट में `GITHUB_TOKEN` सेट करें।

## Sanity

बिल्ट-इन `sanity()` एडैप्टर एक GROQ क्वेरी चलाता है और हर डॉक्युमेंट के फ़ील्ड्स को फ़्रंटमैटर से तथा उसकी Portable Text बॉडी को Markdown से मैप करता है। एडैप्टर `@sanity/client` को अपनी रनटाइम डिपेंडेंसी के रूप में घोषित करता है — एक वैकल्पिक पीयर, इसलिए इसे तभी इंस्टॉल करें जब आप इस स्रोत का उपयोग करें।

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, sanity } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      sanity({
        prefix: "guides",
        projectId: "abc123",
        dataset: "production",
        query: `*[_type == "guide"]`,
        // Field paths default to title / slug.current / body / _updatedAt
        fields: { slug: "slug.current", body: "content" },
      }),
    ],
  },
});
```

किसी प्राइवेट डेटासेट के लिए रीड टोकन `SANITY_TOKEN` एनवायरनमेंट वेरिएबल से आता है, जिसे एडैप्टर घोषित करता है। कस्टम Portable Text ब्लॉक टाइप इंजन के `serializers` विकल्प के ज़रिए Blume कंपोनेंट्स से मैप होते हैं, जो तब उपलब्ध होता है जब आप सीधे `sanitySource` बनाते हैं और उसे [`custom()`](#custom-sources) को पास करते हैं। `serializers` सेट करने से स्रोत के पेज MDX के रूप में लिखे जाते हैं, इसलिए कोई सीरियलाइज़र जो कंपोनेंट या डायरेक्टिव लौटाता है, वह रेंडर होता है।

## Notion

बिल्ट-इन `notion()` एडैप्टर किसी Notion डेटाबेस को एक कलेक्शन में बदल देता है: हर पंक्ति एक पेज बन जाती है, उसकी प्रॉपर्टीज़ फ़्रंटमैटर बन जाती हैं, और उसका ब्लॉक ट्री MDX बन जाता है। कॉलआउट, टॉगल, कॉलम और कोड ब्लॉक संबंधित Blume कंपोनेंट्स से मैप होते हैं, और Notion में आप जो टेक्स्ट टाइप करते हैं वह वैसा ही रेंडर होता है जैसा लिखा गया है: किसी पेज में मौजूद `{`, `<` या कोई Markdown कैरेक्टर MDX, JSX या फ़ॉर्मैटिंग के रूप में पढ़े जाने के बजाय एस्केप किया जाता है। वीडियो ब्लॉक तब एक `<YouTube>` एम्बेड बन जाते हैं जब उनमें कोई YouTube लिंक होता है, अन्यथा एक `<video>` प्लेयर, और दोनों ही स्थितियों में ब्लॉक का कैप्शन एक `<Frame>` कैप्शन बन जाता है। किसी मीडिया फ़ाइल के बजाय किसी वीडियो पेज का लिंक (मान लीजिए कोई Vimeo या Loom URL) एक बिल्ड चेतावनी के रूप में रिपोर्ट किया जाता है, और उसका `<video>` प्लेयर उसी पेज की ओर इशारा करता रहता है, जिसे वह चला नहीं सकता — इसके बजाय टेक्स्ट से उस वीडियो को लिंक करें। एडैप्टर `@notionhq/client` (v5 या उसके बाद का) को अपनी रनटाइम डिपेंडेंसी के रूप में घोषित करता है — एक वैकल्पिक पीयर; Blume डेटाबेस को उसके पहले डेटा स्रोत के ज़रिए पढ़ता है।

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, notion } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      notion({
        prefix: "handbook",
        database: "8f2c1e0a4b7d4f3c9e6a5d2b1c0f9e8d", // the id in the database URL
        // Property names default to the title-typed prop / Description / Slug / Order / Status
        // Pages whose Status isn't publishedValue (default "Published") import as drafts
        publishedValue: "Done",
      }),
    ],
  },
});
```

इंटीग्रेशन टोकन `NOTION_TOKEN` एनवायरनमेंट वेरिएबल से आता है (डेटाबेस को अपने इंटीग्रेशन के साथ शेयर करें); एडैप्टर इसे घोषित करता है, इसलिए इसके बिना बिल्ड चेतावनी देता है।

`Status` प्रॉपर्टी डिफ़ॉल्ट रूप से एक पब्लिश गेट है। जिस पेज के Status (कोई status या select प्रॉपर्टी) में `publishedValue` के अलावा कोई भी अन्य मान होता है — जिसका डिफ़ॉल्ट `Published` है — वह `draft: true` के साथ इंपोर्ट होता है, और प्रोडक्शन बिल्ड ड्राफ़्ट हटा देते हैं। बिना Status मान वाला पेज प्रकाशित होता है, और जिस डेटाबेस में यह प्रॉपर्टी नहीं है वह हर पेज प्रकाशित करता है। Notion के डिफ़ॉल्ट status विकल्प Not started, In progress और Done हैं, इसलिए जो डेटाबेस इनका उपयोग करता है उसमें कोई `Published` मान नहीं होता, और वह तब तक कुछ भी प्रकाशित नहीं करता जब तक आप `publishedValue: "Done"` (या जो भी विकल्प प्रकाशित होने का अर्थ रखता हो) सेट नहीं करते। `properties.status` किसी भिन्न नाम वाली प्रॉपर्टी का नाम बताता है; हर पेज को उसके status की परवाह किए बिना इंपोर्ट करने के लिए, इसे किसी ऐसी प्रॉपर्टी की ओर इंगित करें जो डेटाबेस में नहीं है।

**Notion इमेज और वीडियो URL साइन किए हुए होते हैं और समाप्त हो जाते हैं**, इसलिए एडैप्टर उन्हें बिल्ड टाइम पर साइट की एसेट्स में डाउनलोड कर लेता है और रेफ़रेंस दोबारा लिख देता है — कोई CMS एसेट कभी किसी स्टैटिक बिल्ड को खराब नहीं करती। केवल वही फ़ाइल सहेजी जाती है जिसे सर्वर इमेज या वीडियो के रूप में रिपोर्ट करता है (या, जब प्रतिक्रिया यह नहीं बताती, तो वह जिसका URL किसी इमेज या वीडियो एक्सटेंशन का नाम लेता है); बाकी सब कुछ एक बिल्ड चेतावनी के साथ अपना मूल URL बनाए रखता है, इसलिए आपकी साइट के ओरिजिन से मीडिया के अलावा कभी कुछ भी नहीं परोसा जाता। API कॉल एक छोटे रिक्वेस्ट पूल के ज़रिए नियंत्रित गति से किए जाते हैं (एक बार में 3, जो Notion की प्रति-इंटीग्रेशन रेट लिमिट से मेल खाता है) ताकि सैकड़ों पेज वाले डेटाबेस `429` प्रतिक्रियाओं में फँसे बिना इंपोर्ट हो जाएँ; इसे ट्यून करने के लिए स्रोत पर `concurrency` सेट करें।

## Contentful

बिल्ट-इन `contentful()` एडैप्टर Content Delivery API के ज़रिए किसी एक कंटेंट टाइप की एंट्रियाँ पढ़ता है और हर एंट्री की रिच टेक्स्ट बॉडी को Markdown में उतार देता है: शीर्षक, मार्क, लिंक, सूचियाँ, उद्धरण, टेबल और एम्बेड की गई एसेट्स अपने Markdown समकक्षों से मैप होते हैं, और किसी Markdown लॉन्ग-टेक्स्ट फ़ील्ड में रखी बॉडी वैसी ही पास हो जाती है जैसी लिखी गई है, सिवाय इसके कि जो लिंक वेब, मेल, फ़ोन या सापेक्ष पता नहीं है (मान लीजिए कोई `javascript:` URL), वह केवल अपना लेबल बनाए रखता है, जैसा कि रिच टेक्स्ट में होता है। कुछ भी इंस्टॉल करने की ज़रूरत नहीं — एडैप्टर सीधे REST API से संवाद करता है।

```ts blume.config.ts
import { defineConfig } from "blume";
import { contentful, filesystem } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      contentful({
        prefix: "guides",
        space: "abc123",
        contentType: "guide",
        // environment: "master", locale: "en-US"
        // Field ids default to title / description / slug / body, and the
        // date to sys.updatedAt
        fields: { body: "content" },
        // Extra Delivery API query parameters
        params: { "fields.section": "sdk" },
      }),
    ],
  },
});
```

Delivery API टोकन `CONTENTFUL_ACCESS_TOKEN` एनवायरनमेंट वेरिएबल से आता है, जिसे एडैप्टर घोषित करता है। `--preview` के तहत एडैप्टर `CONTENTFUL_PREVIEW_TOKEN` के साथ Preview API के ज़रिए ड्राफ़्ट पढ़ता है। Preview API डिलीवरी टोकन अस्वीकार करता है, इसलिए प्रीव्यू टोकन के बिना `--preview` `CONTENTFUL_ACCESS_TOKEN` पर वापस जाने के बजाय एक स्पष्ट एरर के साथ विफल होता है। एसेट्स डाउनलोड किए जाने के बजाय Contentful के CDN से रेफ़रेंस की जाती हैं — उनके URL स्थिर होते हैं। जब आप सीधे `contentfulSource` बनाते हैं और उसे [`custom()`](#custom-sources) को पास करते हैं, तो कोई एम्बेड की गई एंट्री इंजन के `serializers` विकल्प के ज़रिए, कंटेंट टाइप id के आधार पर, किसी Blume कंपोनेंट से मैप होती है; `serializers` सेट करने से स्रोत के पेज MDX के रूप में लिखे जाते हैं ताकि लौटाए गए कंपोनेंट रेंडर हों, और बिना सीरियलाइज़र वाली एम्बेड की गई एंट्री को एक कमेंट में दर्ज किया जाता है। किसी अन्य एंट्री का लिंक सादे टेक्स्ट के रूप में रेंडर होता है, क्योंकि इंगित करने के लिए कोई रूट नहीं है।

## Payload

बिल्ट-इन `payload()` एडैप्टर Payload REST API (`/api/<collection>`) के ज़रिए किसी कलेक्शन को पढ़ता है और हर डॉक्युमेंट की Lexical बॉडी को Markdown में उतार देता है: पैराग्राफ़, शीर्षक, बुलेट, क्रमांकित और चेक सूचियाँ, उद्धरण, लिंक, अपलोड और हॉरिज़ॉन्टल रूल। किसी टेक्स्ट फ़ील्ड में रखी बॉडी Markdown के रूप में पास हो जाती है, सिवाय इसके कि जो लिंक वेब, मेल, फ़ोन या सापेक्ष पता नहीं है, वह केवल अपना लेबल बनाए रखता है। कुछ भी इंस्टॉल करने की ज़रूरत नहीं।

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, payload } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      payload({
        prefix: "handbook",
        url: "https://cms.example.com",
        collection: "docs",
        // Field paths default to title / description / slug / content / updatedAt
        fields: { body: "richText" },
        // Extra query parameters: where[...], sort
        params: { sort: "title" },
      }),
    ],
  },
});
```

API कुंजी `PAYLOAD_API_KEY` एनवायरनमेंट वेरिएबल से आती है और `users API-Key <key>` के रूप में भेजी जाती है; जब कुंजी किसी अन्य ऑथ-सक्षम कलेक्शन से संबंधित हो, तो `authCollection` सेट करें। केवल प्रकाशित डॉक्युमेंट ही इंपोर्ट होते हैं — `--preview` ड्राफ़्ट का अनुरोध करता है और उन्हें `draft: true` के साथ स्टेज करता है। डॉक्युमेंट `depth: 1` के साथ फ़ेच किए जाते हैं ताकि अपलोड अपने URL साथ लाएँ, और कोई सापेक्ष अपलोड पथ (`/media/x.png`) `url` के सापेक्ष हल होता है। जब आप सीधे `payloadSource` बनाते हैं और उसे [`custom()`](#custom-sources) को पास करते हैं, तो कोई `block` या `inlineBlock` नोड इंजन के `serializers` विकल्प के ज़रिए, `blockType` के आधार पर, किसी Blume कंपोनेंट से मैप होता है। `serializers` सेट करने से स्रोत के पेज MDX के रूप में लिखे जाते हैं ताकि लौटाए गए कंपोनेंट रेंडर हों; किसी Markdown टेक्स्ट फ़ील्ड में रखी बॉडी Markdown ही बनी रहती है।

## Strapi

बिल्ट-इन `strapi()` एडैप्टर Strapi REST API (`/api/<pluralApiId>`) के ज़रिए किसी कंटेंट टाइप को पढ़ता है और हर एंट्री की Blocks बॉडी को Markdown में उतार देता है: पैराग्राफ़, शीर्षक, सूचियाँ, उद्धरण, कोड ब्लॉक, इमेज और लिंक। कोई Markdown रिच टेक्स्ट फ़ील्ड वैसा ही पास हो जाता है जैसा लिखा गया है, सिवाय इसके कि जो लिंक वेब, मेल, फ़ोन या सापेक्ष पता नहीं है, वह केवल अपना लेबल बनाए रखता है। Strapi 5 की प्रतिक्रियाएँ जैसी हैं वैसी ही पढ़ी जाती हैं, और Strapi 4 के `attributes` एनवलप को फ़्लैट कर दिया जाता है ताकि वही फ़ील्ड पथ लागू हों। कुछ भी इंस्टॉल करने की ज़रूरत नहीं।

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, strapi } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      strapi({
        prefix: "guides",
        url: "https://cms.example.com",
        contentType: "guides",
        // locale: "en"
        // Field paths default to title / description / slug / content / updatedAt
        fields: { body: "body" },
        // Extra query parameters: filters[...], sort
        params: { "filters[section][$eq]": "sdk" },
      }),
    ],
  },
});
```

API टोकन `STRAPI_API_TOKEN` एनवायरनमेंट वेरिएबल से आता है और बेयरर टोकन के रूप में भेजा जाता है। एंट्रियाँ `populate=*` के साथ फ़ेच की जाती हैं ताकि इमेज अपने URL साथ लाएँ (इसे सीमित करने के लिए `populate` सेट करें), और कोई सापेक्ष अपलोड पथ (`/uploads/x.png`) `url` के सापेक्ष हल होता है। केवल प्रकाशित एंट्रियाँ ही इंपोर्ट होती हैं — `--preview` ड्राफ़्ट का अनुरोध करता है (Strapi 5 पर `status=draft`, Strapi 4 पर `publicationState=preview`) और हर उस डॉक्युमेंट को `draft: true` के साथ स्टेज करता है जो कभी प्रकाशित नहीं हुआ; कोई प्रकाशित डॉक्युमेंट अपने नवीनतम ड्राफ़्ट का प्रीव्यू दिखाता है।

## प्रीव्यू और सिंक [#preview-and-sync]

दो फ़्लैग यह नियंत्रित करते हैं कि रिमोट कंटेंट कैसे फ़ेच किया जाता है और क्या-क्या शामिल होता है:

- **`--preview`** — `blume dev` या `blume build` पर यह ड्राफ़्ट रेंडर करता है और अप्रकाशित CMS कंटेंट खींचता है — Sanity अपने `previewDrafts` परिप्रेक्ष्य पर स्विच कर जाता है, Notion `Status` के आधार पर फ़िल्टर करना बंद कर देता है, Contentful Preview API के ज़रिए पढ़ता है, और Payload तथा Strapi ड्राफ़्ट का अनुरोध करते हैं। इस फ़्लैग के बिना प्रोडक्शन बिल्ड हमेशा की तरह ड्राफ़्ट को बाहर रखते हैं, इसलिए प्रीव्यू बिल्ड अप्रकाशित काम को शिप होने से पहले समीक्षा करने का एक सुरक्षित तरीका है।
- **`blume sync`** हर रिमोट स्रोत को फिर से फ़ेच करता है और रनटाइम को दोबारा जेनरेट करता है। डेव कैश-फ़र्स्ट है — कोई रिमोट स्रोत एक बार फ़ेच किया जाता है और पुनः आरंभ पर `.blume/cache` से परोसा जाता है (तेज़ और ऑफ़लाइन-सहिष्णु), इसलिए `blume sync` वह तरीका है जिससे आप डेव सर्वर को पुनः आरंभ किए बिना नवीनतम CMS कंटेंट खींचते हैं (चल रहा सर्वर हॉट-रीलोड करता है)। पहले कैश हटाने के लिए `--force` जोड़ें, या अपने आप रीफ़्रेश करने के लिए किसी स्रोत पर `pollInterval` सेट करें।

```sh
blume dev --preview      # author workflow: see drafts live
blume build --preview    # render a full preview build
blume sync               # refresh remote content now
blume sync --force       # ...ignoring any cached snapshot
```

## कस्टम स्रोत [#custom-sources]

`ContentSource` इंटरफ़ेस को लागू करने वाला कोई भी ऑब्जेक्ट `custom()` को पास किया जा सकता है, और इसी तरह कस्टम सीरियलाइज़र वाला कोई एडैप्टर — या कोई भी ऐसा बैकएंड जो बिल्ट-इन नहीं है — बिना अपने SDK को कोर इंस्टॉल तक पहुँचाए जुड़ जाता है:

```ts blume.config.ts
import { defineConfig } from "blume";
import { custom, filesystem } from "blume/sources";
import { sanitySource } from "blume/sources/sanity.ts";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      custom(
        sanitySource({
          name: "guides",
          prefix: "guides",
          projectId: "abc123",
          dataset: "production",
          query: `*[_type == "guide"]`,
          // Map custom Portable Text blocks to Blume components
          serializers: {
            callout: (block) => `<Callout>${block.text}</Callout>`,
          },
        })
      ),
    ],
  },
});
```

Blume की किसी इंजन फ़ैक्टरी से बनाया गया स्रोत, जैसे ऊपर का `sanitySource`, चल रहे कमांड के कॉन्टेक्स्ट पर दोबारा बनाया जाता है, इसलिए यह `--preview` के तहत ड्राफ़्ट पढ़ता है और बिल्ट-इन एडैप्टर की तरह ही अपना स्नैपशॉट `.blume/cache` में रखता है। आपका अपना स्रोत भी `withContext(ctx)` लागू करके और उस कॉन्टेक्स्ट पर दोबारा बनाए गए स्वयं को लौटाकर यही कर सकता है।

एक स्रोत अपने नेटिव आकार (Portable Text, Notion ब्लॉक, रिमोट HTML) को Markdown/MDX टेक्स्ट में नॉर्मलाइज़ कर देता है, इसलिए पेज चाहे कहीं से भी आए, वही कंपोनेंट और मार्कडाउन फ़ीचर लागू होते हैं। बिल्ट-इन एडैप्टर रिच टेक्स्ट को उतारते समय उसे एस्केप करते हैं, इसलिए किसी लेखक ने CMS में जो टाइप किया — कोई `{`, कोई `<b>`, `import` से शुरू होने वाला कोई पैराग्राफ़, या `&copy;` — वह वैसा ही रेंडर होता है जैसा लिखा गया है। लिंक केवल `http(s)`, `mailto:`, `tel:` और सापेक्ष लक्ष्य बनाए रखते हैं; कोई भी अन्य स्कीम (`javascript:`, `data:`) लिंक के टेक्स्ट के रूप में रेंडर होती है, और कोई स्रोत जो SVG इमेज डाउनलोड करता है, उन्हें सैंडबॉक्स करके परोसा जाता है। `githubReleases()` के रिलीज़ नोट्स और `mdxRemote()` की फ़ाइलों को आपका अपना कंटेंट माना जाता है: उनका रॉ HTML वैसा ही रेंडर होता है जैसा लिखा गया है, इसलिए उन्हें केवल उन्हीं रिपॉज़िटरी की ओर इंगित करें जिन पर आप भरोसा करते हैं। बिल्ट-इन एडैप्टर के विपरीत, `custom()` सादे डेटा के बजाय एक लाइव इंस्टेंस रखता है, इसलिए यह अपनी कोई रनटाइम डिपेंडेंसी या सीक्रेट घोषित नहीं करता — इंस्टेंस उन्हें स्वयं संभालता है।

लोकल फ़ाइलें पढ़ने वाले किसी कस्टम स्रोत को हर एंट्री पर `sourcePath` और स्वयं स्रोत पर `contentRoot` सेट करना चाहिए। `sourcePath` डायग्नोस्टिक्स में फ़ाइल का नाम बताता है और उसके बगल की सापेक्ष इमेज हल करता है; `contentRoot` उस git `log` की सीमा तय करता है जो पेजों को तिथि देता है, इसलिए इसके बिना स्रोत के पेजों को git से प्राप्त कोई ["Last updated" तिथि](/docs/configuration#last-modified) नहीं मिलती।
