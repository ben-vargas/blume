## Implante em qualquer lugar (estático) [#deploy-anywhere-static]

`blume build` compila sua documentação para HTML, CSS e um índice de busca local em `dist/`. Não há servidor para executar — basta apontar qualquer host estático para a pasta.

| Configuração       | Valor             |
| ------------------ | ----------------- |
| Comando de build   | `blume build`     |
| Diretório de saída | `dist`            |
| Versão do Node     | 22.12 ou superior |

Essas configurações funcionam na Vercel, Netlify, Cloudflare Pages, GitHub Pages, Amazon S3 + CloudFront, ou em qualquer bucket ou CDN. Certifique-se de que `blume` seja uma dependência para que o host possa executar o build.

Um build estático inclui:

- cada página de documentação e página personalizada como HTML estático
- um índice de busca local (Orama por padrão, Pagefind opcional)
- um [`sitemap.xml`](/docs/discoverability/sitemap-and-robots#sitemap) quando a URL do site é conhecida
- um [`robots.txt`](/docs/discoverability/sitemap-and-robots#robots), que aponta para o sitemap quando a URL do site é conhecida
- `llms.txt` e `llms-full.txt` para ferramentas de IA
- páginas de redirecionamento
- [imagens Open Graph](/docs/discoverability/open-graph) pré-renderizadas quando `seo.og.enabled` está ativado

### Defina a URL do seu site [#set-your-site-url]

Sitemaps, tags canônicas, RSS e imagens Open Graph precisam de uma origem absoluta. Na **Vercel**, na **Netlify** e no **Cloudflare Pages**, o Blume a detecta a partir do ambiente da plataforma em tempo de build — nenhuma configuração é necessária.

Defina `site`, uma URL absoluta `http://` ou `https://`, para sobrescrever o valor detectado, ou para fornecer um em hosts que não o expõem (GitHub Pages, S3, uma CDN personalizada). Em um build estático, isso vai no objeto `deployment` simples:

```ts blume.config.ts lineNumbers
deployment: {
  site: "https://docs.example.com",
}
```

Na Vercel e na Netlify, a detecção automática prefere seu domínio de produção estável em vez das URLs de pré-visualização de cada deploy, de modo que a origem canônica permanece a mesma entre implantações. O Cloudflare Pages expõe apenas a URL da implantação atual (`CF_PAGES_URL`), que muda a cada deploy, então defina `site` lá.

Durante o `blume dev`, a URL do site recorre ao seu servidor de desenvolvimento local (por exemplo, `http://localhost:4321`) quando nenhuma é definida, para que os recursos que dependem do site — imagens Open Graph, canônicas, o sitemap — funcionem imediatamente. Os builds nunca usam esse fallback, então a saída de produção nunca aponta para o localhost.

## Pré-visualize localmente [#preview-locally]

Antes de publicar, pré-visualize o build de produção exatamente como um host estático o serviria:

```bash
blume build
blume preview
```

`blume preview` serve builds estáticos e builds de servidor com `node()` e `cloudflare()`. Os adaptadores da Vercel e da Netlify não têm servidor de pré-visualização local, então, depois de um build de servidor com `vercel()` ou `netlify()`, ele para com um erro. Teste o site com `blume dev` ou implante uma pré-visualização com `vercel deploy` ou `netlify deploy`.

## Implantações em subcaminho [#subpath-deploys]

Está servindo a documentação sob um caminho como `example.com/docs`? Defina `base` — comum em sites de projeto do GitHub Pages. O site inteiro, incluindo a raiz, passa a ficar sob a base, e os links internos e os recursos são reescritos para incluí-la.

```ts blume.config.ts lineNumbers
deployment: {
  base: "/docs",
}
```

`base` (e `site`) também são opções de todos os adaptadores de host: `vercel({ base: "/docs" })`.

Cada página mantém seu próprio caminho sob a base, mesmo em uma pasta de conteúdo que tenha o mesmo nome da base: com `base: "/docs"`, `docs/setup.md` é servido em `/docs/docs/setup`, e sua URL canônica, seu link na barra lateral e sua entrada no `llms.txt` apontam para lá. Um link relativo à raiz que você escreve e que já começa com a base é considerado como já incluindo-a e fica como foi escrito, então crie o link para essa página com um link relativo (`./docs/setup`) ou com o caminho completo (`/docs/docs/setup`).

## Monte a documentação sob um caminho [#mount-the-docs-under-a-path]

`basePath` monta todas as rotas geradas sob um segmento (`/docs/getting-started`) sem alterar a barra lateral — o nível superior são suas seções, não um grupo envoltório. Use-o quando a documentação fica em `/docs/*` mas a raiz do site continua sendo sua (como o `routeBasePath` do Docusaurus ou o `baseUrl` do Fumadocs).

```ts blume.config.ts lineNumbers
basePath: "/docs",
```

Escreva os links como se estivessem montados na raiz (`/getting-started`); o Blume os reescreve, junto com os redirecionamentos, o sitemap, as URLs canônicas, as imagens Open Graph, o `llms.txt` e o índice de busca. Os recursos públicos (imagens, arquivos em `public/`) permanecem na raiz do site, ou sob [`base`](#subpath-deploys), quando você define uma.

Este é um conceito distinto dos dois caminhos acima:

- Um [`prefix`](/docs/content/sources#adapters) por fonte dá um namespace a **uma** fonte e **adiciona** um grupo na barra lateral.
- `deployment.base` é o subdiretório do host a partir do qual **toda** a aplicação é servida. Os dois se combinam — com ambos definidos, uma página fica em `{deployment.base}/{basePath}/page`.

## Renderização no servidor [#server-rendering]

A saída estática atende à maioria das documentações. Mude para a saída de servidor quando precisar de recursos em tempo de requisição — sobretudo o endpoint do [assistente](/docs/configuration/assistant) e o [servidor MCP](/docs/discoverability/mcp). Você faz isso indicando o host: `deployment` recebe um adaptador importado de `blume/deploy`.

```ts blume.config.ts lineNumbers
import { defineConfig } from "blume";
import { vercel } from "blume/deploy";

export default defineConfig({
  deployment: vercel(),
});
```

Todo adaptador recebe as mesmas opções nomeadas — `site`, `base` e `output` — e repassa qualquer outra coisa sem alterações ao adaptador `@astrojs/*` subjacente, de modo que uma opção que o Blume não nomeia ainda chega até ele:

```ts blume.config.ts lineNumbers
deployment: vercel({
  site: "https://docs.example.com",
  // Passed straight to @astrojs/vercel.
  isr: { expiration: 60 },
}),
```

| Adaptador | Pacote | Usar para |
| --- | --- | --- |
| `vercel()` | `@astrojs/vercel` | Vercel — o caminho mais refinado |
| `netlify()` | `@astrojs/netlify` | Netlify Functions |
| `node()` | `@astrojs/node` | Servidores Node auto-hospedados, contêineres |
| `cloudflare()` | `@astrojs/cloudflare` | Cloudflare Workers e Pages |

`vercel()` e `node()` já vêm com o Blume — basta escolher um e funciona. `netlify()` e `cloudflare()` precisam ter seu pacote instalado no seu projeto (por exemplo, `bun add -d @astrojs/netlify`). Se ele estiver faltando, o `blume build` para e mostra o comando de instalação para o seu gerenciador de pacotes, o `blume dev` avisa e o [`blume doctor`](/docs/cli/doctor) informa o problema. Com o pnpm 10 ou superior, aprove também os scripts de build que esses pacotes trazem (`sharp`, e `workerd` para a Cloudflare) em `allowBuilds` no `pnpm-workspace.yaml`, ou o pnpm interrompe a instalação.

Indicar um adaptador muda o build para a saída de servidor. Para manter um build estático nesse host — com a detecção do site e os arquivos de plataforma que ele lê — passe `output: "static"`:

```ts blume.config.ts lineNumbers
deployment: netlify({ output: "static" }),
```

Um build de servidor inclui tudo o que um build estático inclui, além de quaisquer endpoints ou middlewares do Astro que você adicionar. O adaptador `node()` produz um servidor autônomo que você pode executar diretamente com `node dist/server/entry.mjs`. Ele escuta em `localhost:4321`, a menos que você defina as variáveis de ambiente `HOST` e `PORT` ao iniciá-lo (`HOST=0.0.0.0 PORT=8080 node dist/server/entry.mjs`); `host` e `port` passados para `node()` não têm efeito, porque o `@astrojs/node` os substitui pelas próprias configurações de servidor do Astro. O servidor resolve seus pacotes por meio de links para o `node_modules` do seu projeto, então implante o projeto com suas dependências instaladas, e não apenas o `dist/`. Quando o site publica arquivos de descoberta, serve imagens que uma fonte de conteúdo baixou ou configura redirecionamentos, o Blume coloca um pequeno wrapper na frente do ponto de entrada do Astro (movido para `astro-entry.mjs`, ao lado dele). Ele envia os arquivos de descoberta em `.well-known` com seus tipos de mídia e cabeçalhos CORS e os SVGs baixados em sandbox, algo que o handler estático do servidor autônomo não consegue fazer por conta própria, e responde a cada redirecionamento com o status configurado.

Um build de servidor com `cloudflare()` é implantado com `npx wrangler deploy` a partir da raiz do projeto, depois do `blume build`: o Blume grava a configuração redirecionada do Wrangler em `.wrangler/deploy/` (e adiciona `.wrangler/` ao `.gitignore`) e dá ao Worker o nome do seu projeto — o `name` do `package.json`, senão o hostname do site, senão a pasta —, a menos que um `wrangler.jsonc` seu na raiz do projeto defina `name`.

Na Vercel e na Cloudflare, um build de servidor também ativa a [negociação de conteúdo com `Accept: text/markdown`](/docs/discoverability/markdown#content-negotiation), de modo que um agente que solicite qualquer página de conteúdo com esse cabeçalho recebe seu espelho em Markdown puro na mesma URL. Na Vercel, o Blume insere reescritas condicionadas ao cabeçalho na configuração de roteamento da implantação; na Cloudflare, ele gera um pequeno Worker na frente do Worker do Astro e aponta `assets.run_worker_first` para todos os caminhos, exceto os recursos de build com fingerprint e os arquivos brutos `.md`, `.txt`, `.json` e `.well-known`, já que, de outra forma, a plataforma serviria as páginas pré-renderizadas — e o seu `404.html` para uma URL que nenhuma página atende — antes de qualquer código de servidor ser executado; esses arquivos isentos mantêm seu caminho rápido sem Worker. Esse Worker também responde aos documentos JSON pré-renderizados de cada página (`/api/docs/pages/{route}.json`) a partir do binding de recursos quando uma requisição para um deles chega até ele, já que, de outra forma, o Astro a encaminharia para a rota catch-all de `/api/`.

:::note
`vercel` e `cloudflare` também são os nomes de dois [adaptadores de analytics](/docs/configuration/analytics). Quando uma configuração usa ambos, dê um alias a uma das importações: `import { cloudflare as cloudflareDeploy } from "blume/deploy"`.
:::

:::note
Os recursos de servidor têm sua própria configuração — por exemplo, o assistente precisa de uma chave de API de modelo. Consulte o [guia do assistente](/docs/configuration/assistant) para a configuração.
:::

## Redirecionamentos [#redirects]

Mapeie URLs antigas para novas em `blume.config.ts`:

```ts blume.config.ts
redirects: [{ from: "/old", to: "/new", status: 301 }],
```

`status` aceita `301`, `302`, `307` ou `308` (padrão `301`). Os builds de servidor respondem aos redirecionamentos em tempo de requisição com o status configurado. Os builds estáticos geram páginas de redirecionamento **e** os arquivos de plataforma que seu host lê, para que ele emita um redirecionamento HTTP real: `_redirects` para `netlify()` e `cloudflare()`, `vercel.json` para `vercel()` e — quando nenhum host é indicado — ambos, além de `blume-redirects.json`, um manifesto estruturado para qualquer outro caso (regras de nginx/Apache, um edge worker). Um `_redirects` ou `vercel.json` que você inclua em `public/` permanece intocado.

Dois hosts precisam de mais do que o arquivo:

- A **Netlify** serve um arquivo existente antes de uma regra de redirecionamento, a menos que a regra seja forçada, e um build estático tem uma página de redirecionamento em cada `from`. O `_redirects` para `netlify()` força suas regras (`/old /new 301!`). A Cloudflare rejeita essa flag, então o arquivo gravado por um build sem host indicado a omite, e, na Netlify, esse build responde com a página de redirecionamento; indique o host com `netlify({ output: "static" })` para obter o redirecionamento HTTP.
- A **Vercel** lê o `vercel.json` do diretório raiz do projeto, nunca do diretório de saída, então a cópia em `dist/` só se aplica quando você implanta essa própria pasta com a CLI da Vercel (`vercel deploy dist`). Um projeto conectado ao Git nunca a lê: ele serve as páginas de redirecionamento e nenhum dos cabeçalhos de [Tipos de conteúdo](#content-types). Copie os `redirects` e `headers` de `dist/vercel.json` para o `vercel.json` no diretório raiz do seu projeto, ou use `vercel()` para um build de servidor, cuja configuração de roteamento carrega os redirecionamentos e os cabeçalhos de descoberta.

:::note
`from` e `to` são caminhos exatos — um segmento `:param` ou um curinga `*` (por exemplo, `/blog/:slug` ou `/old/*`) falha na validação da configuração, já que os hosts divergem quanto a padrões. Se você precisar de regras baseadas em padrões, trate-as em um arquivo de infraestrutura como o `vercel.json` (que suporta padrões com curinga em `source`) ou na configuração de redirecionamento do seu host. Um `vercel.json` que você inclua em `public/` é preservado como está.
:::

:::note
Escreva tanto `from` quanto `to` como se estivessem montados na raiz, começando com `/` (`to` também pode ser uma URL `https://` completa) — tanto sob [`base`](#subpath-deploys) quanto sob [`basePath`](#mount-the-docs-under-a-path), o Blume reescreve os dois lados para você, de modo que o redirecionamento fica dentro da base. Um `to` que aponta para um arquivo em `public/` (`/files/guide.pdf`) recebe `base`, mas não `basePath`, já que é lá que o arquivo é servido. Uma base que você já tenha escrito manualmente em `to` é preservada, e não duplicada.
:::

## Tipos de conteúdo [#content-types]

Quando o host lê esse arquivo, um build também gera um arquivo `_headers` que fixa `charset=utf-8` nos endpoints brutos prontos para IA — `/<route>.md`, `/<route>.mdx` e os arquivos `.txt` (`llms.txt`, `llms-full.txt`). Essas respostas são UTF-8 válido, mas muitos hosts estáticos as servem como `text/markdown` / `text/plain` **sem** charset, e então os navegadores recorrem ao Windows-1252 — de modo que documentações não-ASCII (japonês, latim acentuado, …) aparecem como mojibake quando a URL bruta é aberta diretamente. As páginas HTML não são afetadas porque carregam `<meta charset>`. A Netlify lê o `_headers` em uma implantação estática, e a Cloudflare (Pages e recursos estáticos de Workers) tanto em builds estáticos quanto de servidor, então esses adaptadores e um host estático não indicado recebem o arquivo; a Vercel (cujos cabeçalhos vão na configuração de roteamento) e o Node (cujo servidor ignora o arquivo) não recebem. Em vez disso, um build de servidor da Netlify grava as mesmas regras nos `headers` da configuração da sua Frameworks API (`.netlify/v1/config.json`). Já um build estático da Vercel grava as mesmas regras em `dist/vercel.json`, que um projeto conectado ao Git não lê (consulte [Redirecionamentos](#redirects)). Um `_headers` que você inclua em `public/` permanece intocado.

## Variáveis de ambiente [#environment-variables]

Quando um recurso precisa de um segredo em tempo de execução, o Blume avisa no `blume dev`/`build` caso ele esteja faltando — assim o problema aparece cedo, em vez de na primeira requisição:

| Recurso | Variável |
| --- | --- |
| Assistente (AI Gateway) | `AI_GATEWAY_API_KEY` (ou OIDC da Vercel) |
| Assistente (outros adaptadores) | a variável de ambiente padrão da chave do adaptador (`OPENROUTER_API_KEY`, `LLMGATEWAY_API_KEY`, `INKEEP_API_KEY`), ou o `apiKeyEnv` que você passou a ele |
| Busca Mixedbread | `MIXEDBREAD_API_KEY` |
| [Fontes de conteúdo](/docs/content/sources) | `NOTION_TOKEN` (`notion()`), `SANITY_TOKEN` (`sanity()`), `CONTENTFUL_ACCESS_TOKEN` (`contentful()`), `PAYLOAD_API_KEY` (`payload()`), `STRAPI_API_TOKEN` (`strapi()`), `GITHUB_TOKEN` (`githubReleases()` e `mdxRemote()` lendo do GitHub) |

Defina-as no `.env.local` para o desenvolvimento local e no ambiente do seu host para produção. Uma fonte de conteúdo lê seu token ao buscar o conteúdo, durante o `blume dev` e o `blume build`, então defina-o onde o build do seu site é feito. Os segredos em tempo de build para a sincronização do índice de busca (Algolia, Orama Cloud, Typesense) são avisados separadamente durante a etapa de sincronização.

## Cache de build [#build-cache]

O Blume mantém dois caches que um build pode reaproveitar. Os caches do Astro e do Vite ficam em `.blume/.cache/` (entre eles, o armazenamento de conteúdo e as transformações de imagem). Os [cards OG](/docs/discoverability/open-graph#card-cache) renderizados ficam em `node_modules/.cache/blume/og`, de modo que um novo build renderiza apenas os cards cujo título, descrição ou identidade visual mudou. Se uma plataforma mantém esse diretório entre implantações varia:

- A **Vercel** restaura `node_modules/**` a partir do seu cache de build, então os cards são aproveitados (o cache tem 1 GB, é mantido por um mês e é separado por branch — uma nova branch começa a partir do cache de produção).
- A **Netlify** restaura `node_modules`, então os cards são aproveitados.
- O **Cloudflare Workers Builds** persiste apenas os caches do gerenciador de pacotes e, para um projeto Astro detectado, `node_modules/.astro` — nunca `node_modules/.cache` — então cada implantação renderiza todos os cards ali.
- O **GitHub Actions** e outros runners que você gerencia não mantêm nada, a menos que você mesmo faça cache do diretório:

```yaml
- uses: actions/cache@v4
  with:
    path: node_modules/.cache/blume/og
    key: blume-og-${{ runner.os }}-${{ hashFiles('**/bun.lock', '**/package-lock.json', '**/pnpm-lock.yaml') }}
    restore-keys: blume-og-${{ runner.os }}-
```

Os cards são identificados pelo conteúdo, então uma chave imprecisa não é problema: um cache restaurado só economiza renderizações, e nunca serve um card errado.

Um comando de instalação descarta o cache em todas as plataformas: o `npm ci` apaga `node_modules` antes de instalar. Mantenha `npm install`, `bun install` ou `pnpm install` como comando de instalação para aproveitar o cache.

## Resumo do build [#build-summary]

Todo build imprime um resumo — modo de saída, adaptador, URL do site resolvida, provedor de busca, contagem de redirecionamentos, status do sitemap e do `llms.txt`, e quaisquer recursos de servidor habilitados — para que você possa confirmar o que foi publicado (incluindo tudo o que foi detectado automaticamente) antes de implantar.
