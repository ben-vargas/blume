title: Fontes de conteúdo
description: >-
  Traga documentação de arquivos locais, de um repositório remoto, de um CMS ou de qualquer backend personalizado — e combine várias fontes em um único site static-first lido em tempo de build.
---

Por padrão, o Blume lê uma pasta de arquivos `.md`/`.mdx`. As **fontes de conteúdo** permitem trazer páginas de outro lugar — um repositório remoto, um CMS ou qualquer backend personalizado — e combinar várias fontes em um único site. As fontes são lidas em tempo de build; o Blume continua static-first.

## O padrão [#the-default]

Sem nenhuma configuração, o Blume varre a raiz do seu conteúdo (`docs`, por padrão) como uma única fonte de sistema de arquivos. As opções de nível superior `content.root`, `content.include` e `content.exclude` são um atalho para essa fonte única — nada a importar, nada a mudar.

```ts blume.config.ts
import { defineConfig } from "blume";

export default defineConfig({
  content: { root: "docs" },
});
```

## Adaptadores [#adapters]

Cada entrada em `content.sources` é um **adaptador**: uma factory importada de `blume/sources` que retorna um descritor simples que o Blume lê em tempo de build. Adicione um array `sources` para compor fontes. Quando `sources` está presente, ele substitui o padrão implícito, portanto inclua uma entrada `filesystem()` para a sua documentação local — e mova `root`, `include` ou `exclude` para dentro dela. O atalho e `sources` não podem ser combinados; o Blume informa qual campo mover.

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, mdxRemote } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      // Local docs at the site root
      filesystem({ root: "docs" }),

      // Remote MDX from a GitHub repo, mounted under /sdk
      mdxRemote({
        prefix: "sdk",
        github: { owner: "acme", repo: "sdk", ref: "main", path: "docs" },
      }),
    ],
  },
});
```

Cada adaptador integrado é uma factory exportada de `blume/sources`, abordada em sua própria seção abaixo, e [`custom()`](#custom-sources) conecta qualquer outro backend. Todo adaptador que recebe um objeto de opções aceita duas opções compartilhadas:

- **`prefix`** coloca as rotas da fonte em um namespace sob `/<prefix>/…`, e também vira o nome da fonte nos diagnósticos e o do seu diretório de cache. Se duas fontes resolverem para a mesma rota, o Blume reporta um erro de build `BLUME_DUPLICATE_ROUTE` — dê a cada fonte um `prefix` distinto.
- **`pollInterval`** (em segundos) faz uma fonte remota refazer a busca nesse intervalo em desenvolvimento, recarregando apenas quando o conteúdo realmente muda. Deixe-o sem definir para buscar uma vez e congelar o conteúdo durante a sessão. Fontes locais (`filesystem()`, `obsidian()`) observam o sistema de arquivos e o ignoram.

`custom(source)` é a exceção: ele recebe uma instância de `ContentSource` em vez de um objeto de opções, então não há onde passar `prefix` ou `pollInterval`. A própria fonte define sua propriedade `prefix`, e a nova busca funciona do jeito que o método `watch` dela implementar.

O descritor de um adaptador também declara o SDK de que ele precisa e as variáveis de ambiente que ele lê, de modo que o projeto gerado declara esse pacote, `blume dev` e `blume build` avisam quando uma variável não está definida, e `blume doctor` lista as fontes configuradas. As opções são validadas quando a configuração é carregada: uma opção obrigatória ausente, uma chave desconhecida ou um objeto `{ type: "…" }` remanescente da 1.x falha com uma mensagem que indica a correção.

Uma única fonte `filesystem()` enraíza a coleção de documentação gerada no próprio diretório dela. Várias fontes de sistema de arquivos precisam compartilhar uma mesma raiz e particioná-la com globs `include` — uma segunda fonte com raiz em outro lugar é reportada como `BLUME_ENTRY_ID_MISMATCH`, para que as páginas dela não deem 404 silenciosamente.

## Obsidian

O adaptador integrado `obsidian()` lê um vault do [Obsidian](https://obsidian.md) no lugar onde ele está. Não há etapa de exportação nem nada gerado dentro do seu repositório: o vault continua sendo a fonte da verdade, e o Blume reduz o dialeto do Obsidian a Markdown conforme carrega.

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, obsidian } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      obsidian({
        prefix: "notes",
        vault: "vault",
        // Vault folder names to skip at any depth, on top of dot-folders
        exclude: ["Templates", "Daily"],
      }),
    ],
  },
});
```

Os `[[Wikilinks]]` viram links de rota, endereçados pelo nome da nota em todo o vault em vez de pelo caminho, do jeito que o Obsidian endereça as notas. Texto de link personalizado (`[[Note|label]]`), âncoras de cabeçalho (`[[Note#Install]]`), caminhos completos (`[[folder/Note]]` e `[[folder/Note.md]]`), os caminhos parciais que a configuração padrão "shortest path when possible" do Obsidian escreve (`[[guides/Note]]`) e a forma `[[Note\|label]]` que o Obsidian escreve dentro de uma célula de tabela — tudo funciona; e uma nota que define `slug` no frontmatter é linkada na rota que esse slug publica. Quando duas notas compartilham um nome, vence a nota cujo caminho completo no vault é exatamente esse nome — o Obsidian resolve um link como caminho antes de resolver como nome — e depois a primeira na ordem do vault (pastas antes de notas, sem diferenciar maiúsculas de minúsculas, como o explorador de arquivos do Obsidian). O Blume avisa apenas quando um wikilink de fato é resolvido por meio de uma colisão dessas; escreva um caminho mais longo para desambiguar. Uma referência de bloco (`[[Note#^id]]`) leva à nota dela sem âncora: os blocos são renderizados sem id em que aterrissar. Uma âncora de cabeçalho é resolvida contra os cabeçalhos reais da nota de destino, correspondidos do jeito que o autocomplete do Obsidian os escreve (com `**bold**`, `` `code` `` e sintaxe de link removidos) e convertidos em slug pela mesma passagem `extractHeadings` que preenche o manifesto da página — de modo que um link para `#Install` cai no cabeçalho, e não em um id que nenhuma página emite. `[[#Install]]` endereça um cabeçalho na própria nota que você está escrevendo. Um link para um cabeçalho que não existe mantém o link da página, descarta a âncora e emite um aviso.

O frontmatter mantém o que o [esquema de página](/docs/content/frontmatter) do Blume aceita, mais qualquer chave que você declare em [`frontmatter.extend`](/docs/content/frontmatter#custom-keys) (ou, para notas daquele `type`, o `frontmatter` de um tipo de conteúdo); toda outra propriedade do Obsidian — campos do Dataview, datas do Templater, `publish` e os próprios `tags`, `aliases` e `cssclasses` do Obsidian — é descartada quando uma nota é reduzida, então um vault escrito com a UI de Properties compila sem erros de frontmatter. `aliases` é descartado em vez de resolvido — alvos de link por alias ainda não são suportados. Uma imagem Markdown relativa ao lado de uma nota (`![chart](./chart.png)`) é servida a partir do vault e, quando o vault fica dentro do seu repositório git, as páginas do vault ganham [datas de "Última atualização"](/docs/configuration#last-modified) derivadas do git, como qualquer outra página. Os links de "Editar esta página" são resolvidos por meio de `github.dir`, então um vault que fica ao lado do app de documentação em um monorepo ainda linka para o arquivo dele; um vault fora do repositório não recebe link.

Diretórios de idioma e snapshots de versão dentro do vault são lidos do mesmo jeito que a fonte de sistema de arquivos os lê: `fr/Note.md` publica sob `/fr/` com [i18n](/docs/content/i18n) configurado, `v1.0/Note.md` sob `/v1.0/` com [versões](/docs/content/versioning), e wikilinks para essas notas apontam para a rota que cada uma publica.

:::note
Um cabeçalho que contém um link recebe sua âncora de manifesto a partir do Markdown do cabeçalho e seu `id` renderizado a partir do conteúdo de texto. Os dois divergem nesse cabeçalho, então um wikilink para ele pode cair na página em vez de na seção.
:::

Um link para uma nota `index` cai na rota da pasta dela, em vez de em um `/index` fantasma. **Um wikilink não resolvido degrada para texto simples com um aviso de build, em vez de quebrar o build**, então um vault no meio de uma refatoração ainda publica. `%%comments%%` de uma única linha são removidos, um wikilink dentro de um comentário HTML (`<!-- [[Draft]] -->`) é deixado em paz, já que o Obsidian também o esconde, e uma nota sem `title` no frontmatter é intitulada pelo nome do arquivo — a mesma regra que o próprio Obsidian aplica. Uma nota `index` é a única exceção: ela nomeia uma rota, e não uma nota, então o título dela recai na derivação usual do Blume (primeiro cabeçalho, depois o segmento humanizado). Código em blocos cercados, indentado e inline passa literalmente, então uma nota que documenta a sintaxe sobrevive.

Pastas que começam com ponto são ignoradas, incluindo o próprio diretório de configuração `.obsidian` do Obsidian e a `.trash` — que o watcher de desenvolvimento também ignora, então mover um painel no app ou mandar uma nota para a lixeira não refaz o build do seu site. Editar uma nota, sim. Os diretórios que nenhuma varredura de conteúdo lê (`node_modules`, `dist`, `.git`, …) também são ignorados, então um vault com raiz no próprio projeto não publica os READMEs das dependências. Symlinks dentro do vault são seguidos, do mesmo jeito que a fonte de sistema de arquivos os segue, então uma pasta compartilhada linkada no vault é publicada junto. Um vault que fica dentro da raiz da fonte de sistema de arquivos precisa ser excluído dela (`filesystem({ root: "docs", exclude: ["vault/**"] })`); o [`blume version <id>`](/docs/cli/version) então o deixa de fora do snapshot, já que o vault continua publicando as próprias notas como atuais.

Ainda não reduzidos: callouts (`> [!note]`) são renderizados como blockquotes simples, embeds (`![[image.png]]`) passam intocados, `%%comments%%` de várias linhas são deixados no lugar e não há grafo de backlinks.

## MDX remoto [#remote-mdx]

O adaptador integrado `mdxRemote()` busca arquivos `.md`/`.mdx` brutos via HTTP. Enumere os arquivos a partir de uma subárvore de um repositório do GitHub (`github`) ou explicitamente contra uma URL base bruta (`url` + `files`):

```ts blume.config.ts
mdxRemote({
  prefix: "sdk",
  url: "https://raw.githubusercontent.com/acme/sdk/main/docs",
  files: ["intro.mdx", "guide.mdx"],
});
```

O token de um repositório privado é lido da variável de ambiente `GITHUB_TOKEN` — o adaptador a declara, então `blume dev` e `blume build` avisam quando ela não está definida. Ele nunca é embutido na sua configuração ou na saída gerada, e é enviado somente para os próprios hosts do GitHub (`api.github.com`, `raw.githubusercontent.com`), nunca para uma base `url` personalizada. Um repositório público funciona sem ele.

As páginas remotas são renderizadas com fidelidade total de MDX-mais-componentes: seus corpos são materializados em um diretório de staging oculto e renderizados pelo Astro junto com a sua documentação local, de modo que callouts, abas e todos os demais componentes do Blume continuam funcionando.

### Cache e builds offline [#caching-and-offline-builds]

Cada fonte remota mantém um snapshot em `.blume/cache/<source>/`. Se uma busca falhar — uma instabilidade de rede ou uma indisponibilidade do CMS — o Blume serve o último snapshot válido conhecido com um aviso, em vez de quebrar o build. O conteúdo de preview e o conteúdo publicado ganham snapshots separados, assim como cada conjunto de opções da fonte, então um build nunca recorre a rascunhos buscados com `--preview`, e editar a `query` ou os `fields` de uma fonte faz uma busca do zero. O cache fica dentro de `.blume/` e é regenerado, nunca versionado.

Em desenvolvimento, uma fonte remota é servida a partir do snapshot dela quando ele existe, então reiniciar o servidor de desenvolvimento não refaz a busca. Execute `blume sync` para trazer o conteúdo mais recente (um servidor de desenvolvimento em execução recarrega a quente) ou `blume sync --force` para descartar os snapshots antes. As fontes locais do sistema de arquivos recarregam a quente normalmente. Para, em vez disso, consultar periodicamente uma fonte remota em busca de alterações, defina nela a opção compartilhada `pollInterval` (em segundos) — o servidor de desenvolvimento refaz a busca nesse intervalo e recarrega apenas quando o conteúdo realmente muda. Deixe-a sem definir para evitar chamadas à API enquanto você trabalha.

## GitHub Releases

O adaptador integrado `githubReleases()` transforma as releases de um repositório em um changelog: cada release vira uma entrada `type: changelog`, de modo que suas notas de versão _são_ o seu changelog — nada a escrever duas vezes. Combinado com a [linha do tempo de changelog](/docs/advanced/changelog) gerada, publicar uma release no GitHub entrega uma entrada de changelog.

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, githubReleases } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "content" }),
      githubReleases({
        prefix: "changelog",
        owner: "acme",
        repo: "sdk",
        // prereleases: false,  // include prereleases (default off)
        // drafts: false,       // include drafts (needs a write token)
        // limit: 100,          // cap releases, newest-first
      }),
    ],
  },
});
```

Cada release é mapeada automaticamente para os campos do changelog: seu nome (ou tag) vira o título, sua data de publicação define a ordem da linha do tempo, a tag vira `changelog.version`, e as prereleases são marcadas como `Prerelease` (as demais como `Release`). As notas são renderizadas como o corpo da entrada, com duas mudanças nos links: um link que não seja um endereço web, de e-mail, de telefone ou relativo (uma URL `javascript:`, digamos) mantém apenas o rótulo, e um link de volta para o seu próprio [`deployment.site`](/docs/deployment) é reescrito para o caminho relativo à raiz, de modo que acompanha os deploys de preview e a base do seu deploy. Dê à fonte um `prefix` para que suas páginas de release fiquem aninhadas sob uma rota como `/changelog/v1-2-0`.

Um repositório privado se autentica com a variável de ambiente `GITHUB_TOKEN` — o mesmo token que os outros recursos do GitHub usam, nunca embutido na sua configuração; o adaptador a declara, então um build sem ela emite um aviso. Como toda fonte remota, ela é armazenada em cache em `.blume/cache/<source>/` e servida offline se a API estiver inacessível. Como um changelog é complementar, uma falha de busca sem cache (digamos, um build de CI sem token) degrada para um changelog vazio com um aviso, em vez de quebrar o build — defina `GITHUB_TOKEN` nos seus ambientes de CI e de deploy para preenchê-lo.

## Sanity

O adaptador integrado `sanity()` executa uma consulta GROQ e mapeia os campos de cada documento para o frontmatter e seu corpo em Portable Text para Markdown. O adaptador declara `@sanity/client` como sua dependência de runtime — uma dependência peer opcional, então instale-a apenas se você usar esta fonte.

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, sanity } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      sanity({
        prefix: "guides",
        projectId: "abc123",
        dataset: "production",
        query: `*[_type == "guide"]`,
        // Field paths default to title / slug.current / body / _updatedAt
        fields: { slug: "slug.current", body: "content" },
      }),
    ],
  },
});
```

Um token de leitura para um dataset privado vem da variável de ambiente `SANITY_TOKEN`, que o adaptador declara. Tipos de bloco personalizados de Portable Text são mapeados para componentes do Blume por meio da opção `serializers` do motor, disponível quando você constrói `sanitySource` diretamente e o passa para [`custom()`](#custom-sources). Definir `serializers` grava as páginas da fonte como MDX, de modo que um componente ou diretiva retornado por um serializer é renderizado.

## Notion

O adaptador integrado `notion()` transforma um banco de dados do Notion em uma coleção: cada linha vira uma página, suas propriedades viram frontmatter e sua árvore de blocos vira MDX. Callouts, toggles, colunas e blocos de código são mapeados para os componentes correspondentes do Blume, e o texto que você digita no Notion é renderizado do jeito que foi escrito: um caractere `{`, `<` ou de Markdown em uma página é escapado em vez de ser lido como MDX, JSX ou formatação. Blocos de vídeo viram um embed `<YouTube>` quando contêm um link do YouTube e um player `<video>` caso contrário, com a legenda do bloco como legenda de `<Frame>` nos dois casos. Um link para uma página de vídeo em vez de um arquivo de mídia (uma URL do Vimeo ou do Loom, digamos) é reportado como um aviso de build, e o player `<video>` dele continua apontando para a página, que ele não consegue reproduzir — em vez disso, coloque um link para esse vídeo no texto. O adaptador declara `@notionhq/client` (v5 ou posterior) como sua dependência de runtime — uma dependência peer opcional; o Blume lê o banco de dados por meio da primeira fonte de dados dele.

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, notion } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      notion({
        prefix: "handbook",
        database: "8f2c1e0a4b7d4f3c9e6a5d2b1c0f9e8d", // the id in the database URL
        // Property names default to the title-typed prop / Description / Slug / Order / Status
        // Pages whose Status isn't publishedValue (default "Published") import as drafts
        publishedValue: "Done",
      }),
    ],
  },
});
```

O token de integração vem da variável de ambiente `NOTION_TOKEN` (compartilhe o banco de dados com a sua integração); o adaptador a declara, então um build sem ela emite um aviso.

Por padrão, a propriedade `Status` é um controle de publicação. Uma página cujo Status (uma propriedade de status ou de seleção) tenha qualquer valor diferente de `publishedValue`, que por padrão é `Published`, é importada com `draft: true`, e os builds de produção descartam rascunhos. Uma página sem valor de Status é publicada, e um banco de dados sem essa propriedade publica todas as páginas. As opções de status padrão do Notion são Not started, In progress e Done, então um banco de dados que as usa não tem um valor `Published` e não publica nada até você definir `publishedValue: "Done"` (ou a opção que significar publicado). `properties.status` indica uma propriedade com outro nome; para importar todas as páginas independentemente do status, aponte-a para uma propriedade que o banco de dados não tem.

**As URLs de imagem e de vídeo do Notion são assinadas e expiram**, portanto o adaptador as baixa em tempo de build para os assets do site e reescreve as referências — um asset de CMS nunca apodrece um build estático. Só é salvo um arquivo que o servidor informa ser uma imagem ou um vídeo (ou, quando a resposta não informa, um cuja URL indique uma extensão de imagem ou de vídeo); qualquer outra coisa mantém a URL original com um aviso de build, de modo que nada além de mídia é servido a partir da origem do seu site. As chamadas à API são ritmadas por um pequeno pool de requisições (3 por vez, correspondendo ao limite de taxa por integração do Notion), de modo que bancos de dados com centenas de páginas são importados sem esbarrar em respostas `429`; defina `concurrency` na fonte para ajustar isso.

## Contentful

O adaptador integrado `contentful()` lê as entradas de um tipo de conteúdo por meio da Content Delivery API e reduz o corpo em rich text de cada entrada a Markdown: cabeçalhos, marcações, links, listas, citações, tabelas e assets incorporados são mapeados para seus equivalentes em Markdown, e um corpo guardado em um campo de texto longo em Markdown passa do jeito que foi escrito, exceto que um link que não seja um endereço web, de e-mail, de telefone ou relativo (uma URL `javascript:`, digamos) mantém apenas o rótulo, como acontece no rich text. Nada a instalar — o adaptador fala diretamente com a API REST.

```ts blume.config.ts
import { defineConfig } from "blume";
import { contentful, filesystem } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      contentful({
        prefix: "guides",
        space: "abc123",
        contentType: "guide",
        // environment: "master", locale: "en-US"
        // Field ids default to title / description / slug / body, and the
        // date to sys.updatedAt
        fields: { body: "content" },
        // Extra Delivery API query parameters
        params: { "fields.section": "sdk" },
      }),
    ],
  },
});
```

O token da Delivery API vem da variável de ambiente `CONTENTFUL_ACCESS_TOKEN`, que o adaptador declara. Com `--preview`, o adaptador lê rascunhos por meio da Preview API com `CONTENTFUL_PREVIEW_TOKEN`. A Preview API rejeita tokens de delivery, então `--preview` sem um token de preview falha com um erro claro, em vez de recorrer ao `CONTENTFUL_ACCESS_TOKEN`. Os assets são referenciados a partir da CDN do Contentful em vez de serem baixados — as URLs deles são estáveis. Uma entrada incorporada é mapeada para um componente do Blume por meio da opção `serializers` do motor, indexada pelo id do tipo de conteúdo, quando você constrói `contentfulSource` diretamente e o passa para [`custom()`](#custom-sources); definir `serializers` grava as páginas da fonte como MDX para que os componentes retornados sejam renderizados, e uma entrada incorporada sem serializer é sinalizada em um comentário. Um link para outra entrada é renderizado como texto simples, já que não há rota para onde apontar.

## Payload

O adaptador integrado `payload()` lê uma coleção por meio da API REST do Payload (`/api/<collection>`) e reduz o corpo em Lexical de cada documento a Markdown: parágrafos, cabeçalhos, listas com marcadores, numeradas e de verificação, citações, links, uploads e linhas horizontais. Um corpo guardado em um campo de texto passa como Markdown, exceto que um link que não seja um endereço web, de e-mail, de telefone ou relativo mantém apenas o rótulo. Nada a instalar.

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, payload } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      payload({
        prefix: "handbook",
        url: "https://cms.example.com",
        collection: "docs",
        // Field paths default to title / description / slug / content / updatedAt
        fields: { body: "richText" },
        // Extra query parameters: where[...], sort
        params: { sort: "title" },
      }),
    ],
  },
});
```

A chave de API vem da variável de ambiente `PAYLOAD_API_KEY` e é enviada como `users API-Key <key>`; defina `authCollection` quando a chave pertencer a outra coleção com autenticação habilitada. Apenas documentos publicados são importados — `--preview` solicita rascunhos e os coloca em staging com `draft: true`. Os documentos são buscados com `depth: 1` para que os uploads tragam suas URLs, e um caminho de upload relativo (`/media/x.png`) é resolvido em relação a `url`. Um nó `block` ou `inlineBlock` é mapeado para um componente do Blume por meio da opção `serializers` do motor, indexada por `blockType`, quando você constrói `payloadSource` diretamente e o passa para [`custom()`](#custom-sources). Definir `serializers` grava as páginas da fonte como MDX para que os componentes retornados sejam renderizados; um corpo guardado em um campo de texto em Markdown continua sendo Markdown.

## Strapi

O adaptador integrado `strapi()` lê um tipo de conteúdo por meio da API REST do Strapi (`/api/<pluralApiId>`) e reduz o corpo em Blocks de cada entrada a Markdown: parágrafos, cabeçalhos, listas, citações, blocos de código, imagens e links. Um campo de rich text em Markdown passa do jeito que foi escrito, exceto que um link que não seja um endereço web, de e-mail, de telefone ou relativo mantém apenas o rótulo. As respostas do Strapi 5 são lidas como estão, e o envelope `attributes` do Strapi 4 é achatado para que os mesmos caminhos de campo se apliquem. Nada a instalar.

```ts blume.config.ts
import { defineConfig } from "blume";
import { filesystem, strapi } from "blume/sources";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      strapi({
        prefix: "guides",
        url: "https://cms.example.com",
        contentType: "guides",
        // locale: "en"
        // Field paths default to title / description / slug / content / updatedAt
        fields: { body: "body" },
        // Extra query parameters: filters[...], sort
        params: { "filters[section][$eq]": "sdk" },
      }),
    ],
  },
});
```

O token de API vem da variável de ambiente `STRAPI_API_TOKEN` e é enviado como bearer token. As entradas são buscadas com `populate=*` para que as imagens tragam suas URLs (defina `populate` para restringir isso), e um caminho de upload relativo (`/uploads/x.png`) é resolvido em relação a `url`. Apenas entradas publicadas são importadas — `--preview` solicita rascunhos (`status=draft` no Strapi 5, `publicationState=preview` no Strapi 4) e coloca em staging com `draft: true` cada documento que nunca foi publicado; um documento publicado mostra no preview o seu rascunho mais recente.

## Preview e sincronização [#preview-and-sync]

Duas flags controlam como o conteúdo remoto é buscado e o que é incluído:

- **`--preview`** em `blume dev` ou `blume build` renderiza rascunhos e traz conteúdo não publicado do CMS — o Sanity muda para sua perspectiva `previewDrafts`, o Notion para de filtrar por `Status`, o Contentful lê por meio da Preview API, e o Payload e o Strapi solicitam rascunhos. Builds de produção sem a flag excluem rascunhos normalmente, então um build de preview é uma forma segura de revisar trabalho não publicado antes de ele ir ao ar.
- **`blume sync`** refaz a busca de todas as fontes remotas e regenera o runtime. O ambiente de desenvolvimento é cache-first — uma fonte remota é buscada uma vez e servida a partir de `.blume/cache` ao reiniciar (rápido e tolerante a offline), portanto `blume sync` é como você traz o conteúdo mais recente do CMS sem reiniciar o servidor de desenvolvimento (um servidor em execução recarrega a quente). Adicione `--force` para descartar o cache antes, ou defina `pollInterval` em uma fonte para atualizar automaticamente.

```sh
blume dev --preview      # author workflow: see drafts live
blume build --preview    # render a full preview build
blume sync               # refresh remote content now
blume sync --force       # ...ignoring any cached snapshot
```

## Fontes personalizadas [#custom-sources]

Qualquer objeto que implemente a interface `ContentSource` pode ser passado para `custom()`, e é assim que um adaptador com serializers personalizados — ou qualquer backend não integrado — se conecta sem que seu SDK toque a instalação principal:

```ts blume.config.ts
import { defineConfig } from "blume";
import { custom, filesystem } from "blume/sources";
import { sanitySource } from "blume/sources/sanity.ts";

export default defineConfig({
  content: {
    sources: [
      filesystem({ root: "docs" }),
      custom(
        sanitySource({
          name: "guides",
          prefix: "guides",
          projectId: "abc123",
          dataset: "production",
          query: `*[_type == "guide"]`,
          // Map custom Portable Text blocks to Blume components
          serializers: {
            callout: (block) => `<Callout>${block.text}</Callout>`,
          },
        })
      ),
    ],
  },
});
```

Uma fonte construída com uma das factories de motor do Blume, como a `sanitySource` acima, é reconstruída no contexto do comando em execução, então ela lê rascunhos com `--preview` e mantém seu snapshot em `.blume/cache` do mesmo jeito que o adaptador integrado. Uma fonte sua pode fazer o mesmo implementando `withContext(ctx)` e retornando a si mesma reconstruída nesse contexto.

Uma fonte normaliza seu formato nativo (Portable Text, blocos do Notion, HTML remoto) para texto Markdown/MDX, de modo que os mesmos componentes e recursos de markdown se aplicam, não importa de onde uma página venha. Os adaptadores integrados escapam o rich text conforme o reduzem, então o que um autor digitou no CMS — um `{`, um `<b>`, um parágrafo começando com `import` ou `&copy;` — é renderizado do jeito que foi escrito. Os links mantêm apenas destinos `http(s)`, `mailto:`, `tel:` e relativos; qualquer outro esquema (`javascript:`, `data:`) é renderizado como o texto do link, e as imagens SVG que uma fonte baixa são servidas em sandbox. As notas de versão de `githubReleases()` e os arquivos de `mdxRemote()` são tratados como conteúdo seu: o HTML bruto deles é renderizado do jeito que foi escrito, então aponte-os apenas para repositórios em que você confia. Diferentemente dos adaptadores integrados, `custom()` carrega uma instância viva em vez de dados simples, então não declara nenhuma dependência de runtime nem segredo próprio — a própria instância cuida disso.

Uma fonte personalizada que lê arquivos locais deve definir `sourcePath` em cada entrada e `contentRoot` na própria fonte. O `sourcePath` nomeia o arquivo nos diagnósticos e resolve as imagens relativas ao lado dele; o `contentRoot` delimita o `log` do git que data as páginas, então sem ele as páginas da fonte não recebem [data de "Última atualização"](/docs/configuration#last-modified) derivada do git.
