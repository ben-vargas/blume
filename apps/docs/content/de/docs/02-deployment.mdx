## Überall bereitstellen (statisch) [#deploy-anywhere-static]

`blume build` kompiliert deine Dokumentation zu reinem HTML, CSS und einem lokalen Suchindex in `dist/`. Es muss kein Server betrieben werden — richte einfach einen beliebigen statischen Host auf den Ordner aus.

| Einstellung        | Wert             |
| ------------------ | ---------------- |
| Build-Befehl       | `blume build`    |
| Ausgabeverzeichnis | `dist`           |
| Node-Version       | 22.12 oder neuer |

Diese Einstellungen funktionieren auf Vercel, Netlify, Cloudflare Pages, GitHub Pages, Amazon S3 + CloudFront oder in jedem Bucket bzw. CDN. Stelle sicher, dass `blume` eine Abhängigkeit ist, damit der Host den Build ausführen kann.

Ein statischer Build enthält:

- jede Dokumentations- und benutzerdefinierte Seite als statisches HTML
- einen lokalen Suchindex (standardmäßig Orama, Pagefind optional)
- eine [`sitemap.xml`](/docs/discoverability/sitemap-and-robots#sitemap) und [`robots.txt`](/docs/discoverability/sitemap-and-robots#robots), wenn die Site-URL bekannt ist
- `llms.txt` und `llms-full.txt` für KI-Tools
- Weiterleitungsseiten
- vorgerenderte [Open-Graph-Bilder](/docs/discoverability/open-graph), wenn `seo.og.enabled` aktiviert ist

### Deine Site-URL festlegen [#set-your-site-url]

Sitemaps, Canonical-Tags, RSS und Open-Graph-Bilder benötigen einen absoluten Origin. Auf **Vercel**, **Netlify** und **Cloudflare Pages** erkennt Blume ihn zur Build-Zeit aus der Umgebung der Plattform — keine Konfiguration erforderlich.

Setze `site`, um den erkannten Wert zu überschreiben oder um auf Hosts, die ihn nicht bereitstellen (GitHub Pages, S3, ein eigenes CDN), einen Wert anzugeben. Bei einem statischen Build ist das das einfache `deployment`-Objekt:

```ts blume.config.ts lineNumbers
deployment: {
  site: "https://docs.example.com",
}
```

Bei der automatischen Erkennung bevorzugt Blume deine stabile Produktionsdomain gegenüber Preview-URLs einzelner Deployments, sodass der kanonische Origin über Deployments hinweg gleich bleibt.

Während `blume dev` fällt die Site-URL auf deinen lokalen Dev-Server zurück (z. B. `http://localhost:4321`), wenn keine gesetzt ist, damit Site-abhängige Funktionen — Open-Graph-Bilder, Canonicals, die Sitemap — sofort funktionieren. Builds verwenden diesen Fallback nie, sodass die Produktionsausgabe niemals auf localhost verweist.

## Lokale Vorschau [#preview-locally]

Bevor du veröffentlichst, kannst du den Produktions-Build genau so in der Vorschau ansehen, wie ihn ein statischer Host ausliefern würde:

```bash
blume build
blume preview
```

## Deployments unter einem Unterpfad [#subpath-deploys]

Du lieferst deine Dokumentation unter einem Pfad wie `example.com/docs` aus? Setze `base` — üblich für GitHub-Pages-Projektseiten. Die gesamte Site, einschließlich der Wurzel, wird unter die Basis verschoben, und interne Links sowie Assets werden so umgeschrieben, dass sie die Basis enthalten.

```ts blume.config.ts lineNumbers
deployment: {
  base: "/docs",
}
```

`base` (und `site`) sind auch Optionen jedes Host-Adapters: `vercel({ base: "/docs" })`.

## Die Dokumentation unter einem Pfad einhängen [#mount-the-docs-under-a-path]

`basePath` hängt jede generierte Route unter ein Segment (`/docs/getting-started`), lässt die Seitenleiste dabei aber unverändert — die oberste Ebene sind deine Abschnitte, keine umschließende Gruppe. Verwende es, wenn die Dokumentation unter `/docs/*` liegt, die Site-Wurzel aber dir gehört (wie `routeBasePath` bei Docusaurus oder `baseUrl` bei Fumadocs).

```ts blume.config.ts lineNumbers
basePath: "/docs",
```

Schreibe Links so, als wären sie an der Wurzel eingehängt (`/getting-started`); Blume schreibt sie um — ebenso Weiterleitungen, die Sitemap, kanonische URLs, Open-Graph-Bilder, `llms.txt` und den Suchindex. Öffentliche Assets (Bilder, Dateien unter `public/`) bleiben an der Site-Wurzel.

Dies ist ein anderes Konzept als die beiden obigen Pfade:

- Ein quellenspezifisches [`prefix`](/docs/content/sources#adapters) versieht **eine** Quelle mit einem Namensraum und fügt **sehr wohl** eine Seitenleistengruppe hinzu.
- `deployment.base` ist das Unterverzeichnis des Hosts, aus dem die **gesamte** App ausgeliefert wird. Beide lassen sich kombinieren — sind beide gesetzt, landet eine Seite unter `{deployment.base}/{basePath}/page`.

## Server-Rendering

Statische Ausgabe deckt die meisten Dokumentationen ab. Wechsle zur Server-Ausgabe, wenn du Funktionen zur Anfragezeit benötigst — insbesondere den [Ask AI](/docs/configuration/ask-ai)-Endpunkt und den [MCP-Server](/docs/discoverability/mcp). Dazu gibst du den Host an: `deployment` nimmt einen aus `blume/deploy` importierten Adapter entgegen.

```ts blume.config.ts lineNumbers
import { defineConfig } from "blume";
import { vercel } from "blume/deploy";

export default defineConfig({
  deployment: vercel(),
});
```

Jeder Adapter akzeptiert dieselben benannten Optionen — `site`, `base` und `output` — und leitet alles Weitere unverändert an den zugrunde liegenden `@astrojs/*`-Adapter weiter, sodass auch eine Option, die Blume nicht selbst benennt, dort ankommt:

```ts blume.config.ts lineNumbers
deployment: vercel({
  site: "https://docs.example.com",
  // Passed straight to @astrojs/vercel.
  isr: { expiration: 60 },
}),
```

| Adapter | Paket | Verwendung für |
| --- | --- | --- |
| `vercel()` | `@astrojs/vercel` | Vercel — der ausgereifteste Weg |
| `netlify()` | `@astrojs/netlify` | Netlify Functions |
| `node()` | `@astrojs/node` | Selbst gehostete Node-Server, Container |
| `cloudflare()` | `@astrojs/cloudflare` | Cloudflare Workers und Pages |

`vercel()` und `node()` sind in Blume enthalten — die Auswahl eines der beiden funktioniert einfach. Für `netlify()` und `cloudflare()` muss das jeweilige Paket in deinem Projekt installiert sein (z. B. `bun add -d @astrojs/netlify`). Fehlt es, bricht `blume build` mit dem Installationsbefehl für deinen Paketmanager ab, `blume dev` warnt, und [`blume doctor`](/docs/cli/doctor) meldet es. Ab pnpm 10 musst du außerdem die Build-Skripte, die diese Pakete mitbringen (`sharp` sowie `workerd` für Cloudflare), unter `allowBuilds` in `pnpm-workspace.yaml` freigeben, sonst bricht pnpm die Installation ab.

Die Angabe eines Adapters stellt den Build auf Server-Ausgabe um. Um auf diesem Host einen statischen Build beizubehalten — mit seiner Site-Erkennung und den Plattformdateien, die er liest —, übergib `output: "static"`:

```ts blume.config.ts lineNumbers
deployment: netlify({ output: "static" }),
```

Ein Server-Build enthält alles, was ein statischer Build enthält, sowie alle Astro-Endpunkte oder Middleware, die du hinzufügst. Der `node()`-Adapter erzeugt einen eigenständigen Server, den du direkt mit `node dist/server/entry.mjs` ausführen kannst. Der Server löst seine Pakete über Links in das `node_modules` deines Projekts auf, deploye das Projekt also mit seinen installierten Abhängigkeiten und nicht nur `dist/`. Wenn die Site Discovery-Dateien veröffentlicht, setzt Blume einen kleinen Wrapper vor den Einstiegspunkt von Astro (der daneben nach `astro-entry.mjs` verschoben wird), damit die `.well-known`-Discovery-Dateien mit ihren Medientypen und CORS-Headern ausgeliefert werden, die der statische Handler des eigenständigen Servers nicht selbst setzen kann.

Ein `cloudflare()`-Server-Build wird nach `blume build` mit `npx wrangler deploy` aus dem Projektstammverzeichnis deployt: Blume schreibt die umgeleitete Wrangler-Konfiguration nach `.wrangler/deploy/` (und fügt `.wrangler/` zur `.gitignore` hinzu) und benennt den Worker nach deinem Projekt — nach dem `name` aus `package.json`, andernfalls nach dem Hostnamen der Site, andernfalls nach dem Ordner —, sofern nicht eine eigene `wrangler.jsonc` im Projektstammverzeichnis `name` setzt.

Auf Vercel und Cloudflare aktiviert ein Server-Build außerdem die [Content Negotiation über `Accept: text/markdown`](/docs/discoverability/markdown#content-negotiation), sodass ein Agent, der eine beliebige Inhaltsseite mit diesem Header anfragt, unter derselben URL deren Roh-Markdown-Spiegelung erhält. Auf Vercel fügt Blume header-abhängige Rewrites in die Routing-Konfiguration des Deployments ein; auf Cloudflare erzeugt es einen kleinen Worker vor dem Astro-Worker und richtet `assets.run_worker_first` auf jeden Pfad außer den mit Fingerprint versehenen Build-Assets und den rohen `.md`-, `.txt`-, `.json`- und `.well-known`-Dateien aus, da die Plattform andernfalls die vorgerenderten Seiten — und ihre `404.html` für eine URL, hinter der keine Seite steht — ausliefern würde, bevor Servercode ausgeführt wird; diese ausgenommenen Dateien behalten ihren schnellen Pfad ohne Worker. Dieser Worker beantwortet außerdem Anfragen nach den vorgerenderten JSON-Dokumenten pro Seite (`/api/docs/pages/{route}.json`), die bei ihm ankommen, direkt aus dem Asset-Binding, da Astro sie andernfalls an die `/api/`-Catch-all-Route weiterleiten würde.

:::note
`vercel` und `cloudflare` sind auch die Namen zweier [Analytics-Adapter](/docs/configuration/analytics). Wenn eine Konfiguration beide verwendet, vergib für einen der Importe einen Alias: `import { cloudflare as cloudflareDeploy } from "blume/deploy"`.
:::

:::note
Serverfunktionen haben ihre eigene Konfiguration — Ask AI benötigt beispielsweise einen API-Schlüssel für ein Modell. Zur Einrichtung siehe den [Ask-AI-Leitfaden](/docs/configuration/ask-ai).
:::

## Weiterleitungen [#redirects]

Ordne alte URLs in `blume.config.ts` neuen zu:

```ts blume.config.ts
redirects: [{ from: "/old", to: "/new", status: 301 }],
```

`status` akzeptiert `301`, `302`, `307` oder `308` (Standard `301`). Server-Builds verarbeiten Weiterleitungen zur Anfragezeit. Statische Builds erzeugen Weiterleitungsseiten **und** die Plattformdateien, die dein Host liest, damit er eine echte HTTP-Weiterleitung ausgibt: `_redirects` für `netlify()` und `cloudflare()`, `vercel.json` für `vercel()` und — wenn kein Host angegeben ist — beide sowie `blume-redirects.json`, ein strukturiertes Manifest für alles Übrige (nginx-/Apache-Regeln, ein Edge Worker). Eine `_redirects` oder `vercel.json`, die du in `public/` mitlieferst, bleibt unangetastet.

:::note
`from` und `to` sind exakte Pfade — ein `:param`-Segment oder ein `*`-Platzhalter (z. B. `/blog/:slug` oder `/old/*`) lässt die Konfigurationsvalidierung fehlschlagen, da Hosts Muster unterschiedlich behandeln. Wenn du musterbasierte Regeln brauchst, behandle sie stattdessen in einer Infrastrukturdatei wie `vercel.json` (die Platzhalter-`source`-Muster unterstützt) oder in der Weiterleitungskonfiguration deines Hosts. Eine `vercel.json`, die du in `public/` mitlieferst, bleibt unverändert erhalten.
:::

:::note
Schreibe sowohl `from` als auch `to` so, als wären sie an der Wurzel eingehängt — sowohl unter [`base`](#subpath-deploys) als auch unter [`basePath`](#mount-the-docs-under-a-path) schreibt Blume beide Seiten für dich um, sodass eine Weiterleitung innerhalb der Basis landet. Eine Basis, die du bereits von Hand in `to` geschrieben hast, bleibt erhalten und wird nicht verdoppelt.
:::

## Inhaltstypen [#content-types]

Wo der Host eine solche Datei liest, erzeugt ein Build außerdem eine `_headers`-Datei, die `charset=utf-8` an die rohen, KI-tauglichen Endpunkte heftet — `/<route>.md`, `/<route>.mdx` und die `.txt`-Dateien (`llms.txt`, `llms-full.txt`). Diese Antworten sind gültiges UTF-8, doch viele statische Hosts liefern sie als `text/markdown` / `text/plain` **ohne** Charset aus, und Browser fallen dann auf Windows-1252 zurück — sodass Dokumentation mit Nicht-ASCII-Zeichen (Japanisch, akzentuiertes Latein, …) beim direkten Öffnen der Roh-URL als Zeichensalat dargestellt wird. HTML-Seiten sind davon nicht betroffen, da sie `<meta charset>` mitführen. Netlify liest `_headers` bei einem statischen Deployment und Cloudflare (Pages sowie statische Assets von Workers) sowohl bei statischen als auch bei Server-Builds, daher erhalten diese Adapter und ein nicht angegebener statischer Host die Datei; Vercel (dessen Header über die Routing-Konfiguration laufen) und Node (dessen Server die Datei ignoriert) nicht. Eine `_headers`-Datei, die du in `public/` mitlieferst, bleibt unangetastet.

## Umgebungsvariablen [#environment-variables]

Wenn eine Funktion ein Laufzeit-Secret benötigt, warnt Blume bei `blume dev`/`build`, falls es fehlt — so tritt das Problem früh zutage statt erst bei der ersten Anfrage:

| Funktion | Variable |
| --- | --- |
| Ask AI (AI Gateway) | `AI_GATEWAY_API_KEY` (oder Vercel OIDC) |
| Ask AI (andere Adapter) | die Standard-Schlüssel-Umgebungsvariable des Adapters (`OPENROUTER_API_KEY`, `LLMGATEWAY_API_KEY`, `INKEEP_API_KEY`) oder das `apiKeyEnv`, das du ihm übergeben hast |
| Mixedbread-Suche | `MIXEDBREAD_API_KEY` |

Setze sie in `.env.local` für die lokale Entwicklung und in der Umgebung deines Hosts für die Produktion. Vor fehlenden Build-Zeit-Secrets für die Synchronisierung des Suchindex (Algolia, Orama Cloud, Typesense) wird separat während des Sync-Schritts gewarnt.

## Build-Cache [#build-cache]

Blume verwendet zwei Caches, die ein Build wiederverwenden kann. Die Caches von Astro und Vite liegen unter `.blume/.cache/` (darunter der Content Store und die Bildtransformationen). Gerenderte [OG-Karten](/docs/discoverability/open-graph#card-cache) liegen in `node_modules/.cache/blume/og`, sodass ein erneuter Build nur die Karten rendert, deren Titel, Beschreibung oder Branding sich geändert hat. Ob eine Plattform dieses Verzeichnis zwischen Deployments behält, ist unterschiedlich:

- **Vercel** stellt `node_modules/**` aus seinem Build-Cache wieder her, sodass Karten erhalten bleiben (der Cache ist 1 GB groß, wird einen Monat lang aufbewahrt und ist pro Branch getrennt — ein neuer Branch startet mit dem Produktions-Cache).
- **Netlify** stellt `node_modules` wieder her, sodass Karten erhalten bleiben.
- **Cloudflare Workers Builds** speichert nur Caches des Paketmanagers und, bei einem erkannten Astro-Projekt, `node_modules/.astro` — niemals `node_modules/.cache` —, sodass dort bei jedem Deployment jede Karte neu gerendert wird.
- **GitHub Actions** und andere Runner, die du selbst verwaltest, behalten nichts, es sei denn, du cachst das Verzeichnis selbst:

```yaml
- uses: actions/cache@v4
  with:
    path: node_modules/.cache/blume/og
    key: blume-og-${{ runner.os }}-${{ hashFiles('**/bun.lock', '**/package-lock.json', '**/pnpm-lock.yaml') }}
    restore-keys: blume-og-${{ runner.os }}-
```

Karten werden anhand ihres Inhalts identifiziert, daher ist ein ungenauer Schlüssel kein Problem: Ein wiederhergestellter Cache spart immer nur Render-Vorgänge und liefert nie eine falsche Karte aus.

Ein Installationsbefehl verwirft den Cache auf jeder Plattform: `npm ci` löscht `node_modules` vor der Installation. Verwende weiterhin `npm install`, `bun install` oder `pnpm install` als Installationsbefehl, um von der Wiederverwendung zu profitieren.

## Build-Zusammenfassung [#build-summary]

Jeder Build gibt eine Zusammenfassung aus — Ausgabemodus, Adapter, aufgelöste Site-URL, Suchanbieter, Anzahl der Weiterleitungen, Status von Sitemap und `llms.txt` sowie alle aktivierten Serverfunktionen — damit du vor dem Deployment prüfen kannst, was ausgeliefert wurde (einschließlich aller automatisch erkannten Werte).
